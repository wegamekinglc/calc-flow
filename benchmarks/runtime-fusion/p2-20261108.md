## Fixed scope

Measure Float64 Rows decay on ordinary finite financial-style prices through
the actual owned StreamingRunner. Use the default `stable_v1` profile, normal
GC, four Tokio workers and one entity. All cases have exactly 1,000 history
rows in a 1,000-row history segment. The 1,000-row window is therefore already
full when appends start; history is not spread across 64 entities.

| Case | Indicator                    | Window | History | Entities | Append rows | Role                                    |
|------|------------------------------|--------|---------|----------|-------------|-----------------------------------------|
| 1    | decay                        | 20     | 1000    | 1        | 1024        | Moderate-window target and cost control |
| 2    | decay                        | 1000   | 1000    | 1        | 1024        | Large-window incremental target         |
| 3    | decay plus mean in one stage | 1000   | 1000    | 1        | 1024        | Mixed-stage typed-path target           |
| 4    | decay                        | 1000   | 1000    | 1        | 1           | Direct per-append COW risk control      |

There are exactly four workloads and no Cartesian expansion. The fixed
`scripts/benchmark_suite/decay_warm.py` adapter does not call the older warm
matrix selector, so it cannot silently add a million-row history point.
The ordinary mean/dual-SMA defaults remain available in their existing tool;
P1a's arithmetic/filter indicator is not introduced here.

The first three cases are preregistered targets. All four must complete and
all four are checked for a confirmed slowdown. Only one numerical profile,
GC mode, entity count and worker configuration is measured. Duration frames,
other dtypes, non-finite/adversarial inputs, sparse entity appends, checkpoints,
restore and `stable_v2` performance are unmeasured by this selection; their
correctness requirements remain covered by the product tests.

## Oracle and native activation

The shared warm harness builds a single native Rolling stage containing decay
alone or decay and mean together. It uses existing declarations without adding
schemas or changing graph semantics solely for admission. Confirm final
lowered/compiled shape against the frozen products before acquisition.

For decay, an independent Python oracle traverses each finite fixture frame
oldest first with valid weights W-n+1 through W, matching the old ordered fold.
It validates every warm-up and appended output with rtol=atol=1e-12. This oracle
is outside the sample timer. Identity columns, row order and output counts are
also checked. The neighboring mean in case 3 is checked separately with the
existing mean oracle/tolerance; decay's `max_absolute_error` describes its own
column, while a failed mean also rejects the sample.

Candidate activation/work evidence comes from the real Rust callback counters,
not a Python reconstruction of its work. The frozen candidate exposes private
`_decay_work` dictionaries within each rolling node's data/watermark/end status.
Preserve both before/after raw statuses and their actual counter differences.
Baseline builds without this instrumentation are marked unavailable, never zero.

| Counter family               | Fields                                                                                                    | Interpretation                                                       |
|------------------------------|-----------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------|
| Transitions                  | `transitions`                                                                                             | Actual attempted decay advances                                      |
| Disjoint row classifications | `shortcut_rows`, `certified_rows`, `guard_fallback_rows`, `quota_reference_rows`, `scheduled_reseed_rows` | Their sum must equal transitions                                     |
| Arithmetic/history scans     | `initial_seed_samples`, `scheduled_reseed_samples`, `guard_reseed_samples`, `reference_scan_samples`      | Real Rust slot visits for the respective passes                      |
| Memory/history work          | `cache_copied_samples`, `reference_history_samples`                                                       | Actual owned-cache COW slots and authoritative-history visits/clones |

Initial seeding counts its three passes; scheduled/guard reseeding counts its
fused fold; quota reference counts its count and weighted-fold passes. Use the
author's actual instrumentation semantics and retain zeros/missing-field rules.
The mixed mean's work is not included in `_decay_work`; existing generic rolling
metrics remain separate.

The adapter validates row-class coverage, nonnegative monotonic counters,
nonzero certified rows during appends, and total final transitions matching
history plus the 30 real appends. Unexpected/missing candidate instrumentation
cannot support an activation claim. Retain per-node/callback raw data even when
reporting a per-case sum of the same field.

Arithmetic scan/reseed visits and memory-copy/history visits are reported in
separate columns. Do not add these different work kinds into one operations
figure. The recurrence can have amortized O(N) arithmetic on certified inputs
while each touched entity/group/batch copies up to W retained samples. In the
single-row append case, that memory work can remain O(NW). Do not claim an
unconditional O(N) whole-job implementation or describe Python estimates as
measured native work.
