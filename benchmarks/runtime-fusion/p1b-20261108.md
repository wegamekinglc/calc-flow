## Target and hypothesis

The target is the real Rust example-30 stock-position graph: filter
`flow_type = 'trade'`, compute signed quantity with CASE, then grouped SUM by
account/stock. The candidate shares task execution through the existing local
edge/ready group. Every input batch still emits its full cumulative snapshot.
The expected saving is scheduling/coordination overhead; lost overlap between
Expression and SQL is a risk, especially on the larger-batch control.

The maintained `grouped_sum_state_benchmark` executes this exact graph with
default schema-free ports, checkpointing off and a compact-required budget of
10,000 groups. Its successful completion attests actual compact admission;
merely recognizing SQL syntax does not. The benchmark validates all rows of
every snapshot against an independent arithmetic map, input/output schema and
content hashes, and the native lifecycle/resource status.

The actual Python example-30 document was exported unchanged for the author's
native correctness tests. It has four logical nodes, with CASE/filter→SQL in
the middle and the original `input` SQL alias. No schemas were added to make
it eligible. The author reports the real document forms one middle group,
reducing four physical drivers to three, and the Rust example's absent-schema
pair is also admitted. Record those final tests and their exact source at
implementation handoff. The performance claim will apply to the measured Rust
surface; the Python graph receives correctness/admission coverage.

## Exactly two cases

Both cases use 100 accounts × 100 stocks, a zero-valued seed for every one of
the 10,000 groups, and the same 256,000 subsequent business rows. The fixture
retains the example's buy/sell quantities and 80% trade mix. Inputs contain
266,000 rows in total per invocation.

| Case                           | CPUs / Tokio workers | DataFusion partitions | Source batches                         | Snapshot count | Total emitted snapshot rows |
|--------------------------------|----------------------|-----------------------|----------------------------------------|----------------|-----------------------------|
| `stock-stream-4cpu-batch1000`  | 0,2,4,6 / 4          | fixed 4               | 10 seed batches + 256 business batches | 266            | 2,615,000                   |
| `stock-stream-4cpu-batch64000` | 0,2,4,6 / 4          | fixed 4               | 1 seed batch + 4 business batches      | 5              | 50,000                      |

Small batches exercise the scheduling boundary repeatedly. Larger batches
expose stage-overlap loss on the same graph and group state. No one/eight-CPU,
sparse, finite batch, checkpoint, alternate type or extra scale case is added.

Fixture creation uses the existing Python example's immutable Arrow data
content. It seals exact IPC batch boundaries separately for seeds and business
rows. The Python example's internal 100,000-row template period must not insert
extra boundaries into the 64,000-row case. No runtime batching or output
coalescing is introduced; both native builds read the same sealed IPC input
for each case.

## Maintained collection contract

The fixed adapter is `scripts/benchmark_suite/fusion_sum.py`. It reuses the
existing SUM collector's build validation, comparison, process ownership,
resource sampling, per-snapshot validation, round/case collection, paired
statistics and final journal. It does not change the Rust harness or builder.
The default four-case/two-million-row fixture preparation is not invoked.

- Exactly two rounds of ten AB/BA pairs per case; every side of every pair is
  a fresh native invocation. Each round also has one warmup per arm.
- Total: 80 formal observations and eight warmups, across 88 native jobs.
  The selected fixtures produce 11,924 full snapshot checks across these jobs.
- Native primary timing starts after IPC preload and covers graph construction,
  compilation, execution, retained snapshots, natural EOF and cleanup.
  Independent full snapshot arithmetic/schema/hash validation is outside the
  primary timer and inside the total collection budget.
- Process CPU clocks cover the same primary interval. Whole-process peak RSS
  includes preload, retained snapshots and validation; it is not operator-only
  memory. Affinity and all helper-pool thread settings are validated natively.
- The existing `sql_compact_state_budget`, edge budgets, DataFusion batch size
  and resource settings remain. DataFusion uses fixed p4 with
  `min_rows_per_partition=1`; helper pools use one thread. The controller runs
  on CPU31. Collect and report the actual guest topology.
- Every formal and warmup row must satisfy `validate_sample`, including clocks,
  affinity/threads, mode/partitions, exact input/batch/snapshot/schema identities
  and clean completion with no leftover task, error, metric overflow or epoch.
- Each pair must satisfy the complete cross-version oracle equality check.
  CPU sampling profiles are optional in the maintained tool and are not part
  of this selected task; processing CPU/RSS/status witnesses remain required.

Use the unchanged two-round paired-median interval classifier and +5% rule.
Merge requires at least one preregistered target to receive its actual
`improved` verdict, no confirmed regression in either selected case, and all
correctness, CI/Codacy and final-review gates. Report every interval and
inconclusive outcome. Task admission, smaller driver count or a single timing
cannot substitute for an end-to-end improvement.
