# P1a row-local runtime fusion: measurement protocol

Status: acquisition stopped; no accepted performance improvement.
The unique acquisition used final sealed source and shared harness
`873e735a5be6e47074cd097dbf87f6003ab25ad9`. The preregistration remains
available in that commit; this report records the resulting evidence.

This compares the P1a admission expansion with main `8d8be7d9`. Both
revisions execute the same maintained warm-stream harness. The target lowers to
exactly two native nodes: a 20-row Rolling mean followed by an Expression with
`symbol < 'S032'` and `mean * 2.0 + 1.0`. Python lowering retains the boundary. The normal terminal Expression omits an
output-port schema; the candidate proves its row-local AST without requiring a
new declaration or early schema planning. The focused Rust tests cover this
normal application shape, while unknown schemas cannot justify further links.
The original mean-only workload is the control for the already-admitted
projection path. The arithmetic/filter indicator rejects sparse appends;
existing complete-tick validation also rejects append sizes not divisible by
the entity count, so each supported append retains rows.

## Sustained-input control

The third case addresses loss of stage overlap when two formerly independent
operator tasks are fused. It feeds a finite stream continuously rather than
waiting for each individual append to reach the sink.

- Case: `benchmarks/test_stream_operators.py::test_stream_operator_lifecycle[standard-rolling_arithmetic_filter]`.
- Fixed input: 20,000 rows, 16 entities, 20-row mean, 640-row source batches
  (32 batches including the tail), `symbol < 'S008'`, then `mean * 2 + 1`.
- Fixed output: 10,000 rows, with every sequence and value checked against the
  independent direct rolling-mean oracle before and after timing.
- Timer: the existing Program stream lifecycle-to-Arrow boundary, including
  compilation, startup, source delivery, watermarks, conversion and completion.
- Samples: the maintained release contract, two rounds of ten alternating AB/BA
  pairs. Each observation is a fresh isolated pytest process and retains its
  saved raw samples, machine/dependency/workload identity and sealed native hash.
- Collection reuses the maintained `release_pairs.collect_case/evaluate_case`,
  pytest command/environment builders and observation normalizer. A thin
  task-local adapter selects `standard` scale because the general standalone
  Python collector defaults to `overhead`; it does not change that collector.
- Acceptance: report the maintained release verdict and interval for each round.
  A confirmed regression blocks acceptance. This control has no requirement to
  establish an improvement and its statistics are not combined with warm ratios.

The new case first failed with `unsupported stream operator benchmark`, then
passed with all 20,000 rows checked using the sealed baseline native. This was a
correctness check with `--benchmark-disable`, not a performance acquisition.

## Timing, budget and decision

The timer starts with prepared Data enqueue and ends after sink delivery and
conversion to Arrow. Source/task/channel work, rolling, watermark finalization,
projection and output conversion remain timed. Compilation, startup, history
construction, validation, IPC, checkpointing and shutdown are outside each
sample, but inside the total acquisition budget.

All three cases together have a 600-second wall-clock limit, including setup,
preflight, fixture/history work, warmup, correctness, startup and cleanup.
Expected acquisition time is below 240 seconds: under 60 seconds for the warm
cases and setup, about 140 seconds for 40 sustained-input processes, and cleanup
reserve. Builds remain separate. No further scale, GC mode,
thread count, case, repetition or favorable retry is included.

The target establishes a material speedup only if its paired median speedup
exceeds 1.05 and the maintained bootstrap 95% interval has a lower bound above
1.0. Report the control's full interval and timings, without interpreting an
interval containing 1.0 as proof of equivalence. A control interval wholly below
`1 / 1.05` is evidence of a material regression and prevents acceptance.
Insufficient precision, incompatible identity, incorrect output, budget
exhaustion or an unsuitable environment cannot support a merge.

The host is WSL2. Before acquisition, record current load, available memory,
affinity, native hashes and exact harness hashes. Wait for owned compilation
and tests to finish. Stop rather than classify timings if the environment is
unsuitable. Settle all owned worker processes on completion or failure.

## Results

The unique acquisition stopped after 9.895 seconds. Both warm cases completed
all 30 pairs. The target did not meet the preregistered improvement condition.
The sustained-input collector stopped at its first baseline observation because
its workload descriptor omitted `input_rows` and `output_rows`, while the
benchmark's metadata supplied those values. The maintained identity validator
correctly rejected that mismatch. No retries, added cases or added samples ran.

The control's interval upper bound is above `1 / 1.05`, so the preregistered
material-regression condition is not met. This does not establish equivalence.
The target's interval includes 1.0 and its median is below 1.05. The evidence
cannot support a speedup claim or a merge. These ratios are the maintained warm
bootstrap results, not the release gate's `improved/inconclusive` enum.

The sustained-input pytest process completed and validated all 20,000 input and
10,000 output rows, but its observation failed identity validation before any
accepted pair existed. There is no sustained-input paired verdict and no valid
aggregate acceptance verdict. Raw timing from this rejected observation is
preserved only as evidence of the failed acquisition; it is not a comparison.

All 120 warm append observations passed the strict oracle. All four warm jobs
completed with zero task errors and zero remaining logical tasks. The terminal
RSS observations are preserved in the raw report; they are not peak-memory
measurements or proof of a memory improvement. A post-acquisition process check
found no remaining owned warm workers or selected pytest process.

Before acquisition, no cargo/rustc processes were present, available memory was
26,815,778,816 bytes, and the WSL2 load averages were approximately

## Activation diagnostic

The sealed candidate's actual Python lowering was inspected without recording
new timings. In both warm graphs, Rolling declares exact input and output
schemas. The mean-only output adds nullable Float64 `moving_average`; the
arithmetic/filter output adds nullable Float64 `indicators__cf_roll_0`.
Each following Expression declares the corresponding exact input schema and
omits its output-port schema.

The public `task_count` is the logical task registry count. Both sides report
seven while running, but this cannot establish physical fusion: the supervisor
retains logical registrations even when multiple logical operators share one
physical driver. The crate-private `physical_driver_count` is only compiled for
tests and was not directly instrumented in this measurement.

The [independent admission audit](../../.codex/artifacts/reviews/ta-arroyo-p1a-fusion.md)
followed the real graph through `config::rolling_node`, runtime-node creation,
conversion and every fusion gate. Derived and configured Rolling outputs match;
Join/ASOF-only projection pushdown cannot change this schema. The sole edge is
Internal, topology and exact input schemas match, both Expression output
schema declarations are absent, selected-UDF sets are empty, and the concrete
quoted identifiers/nested binary operations/literals pass the row-local AST
proof. The existing unknown-tail native fixture covers that admission shape.

This static full-chain evidence supports that the candidate admits the real
target. It found no missing application schema or proof to explain the result
as an unimplemented path. Physical-driver activation was not directly measured;
that limitation is retained. No additional compilation or timing experiment
was used to seek a better result.
