# P3 shared Rows history — fixed warm append comparison

The preregistered performance rule passes for this three-case acquisition.
The 10,000-entity dual-mean target achieved a 1.055710× paired median speedup,
with 95% CI [1.012244, 1.075539]. The one-entity target and control remain
inconclusive; neither establishes equivalence or improvement. No selected case
has a confirmed >5% regression under the frozen rule.

This result applies to warm append end-to-end latency in the selected workload,
not whole-job startup/warmup, every rolling query, a general memory reduction,
or an allocation-count claim. Source review and the source CI snapshot are
green; final archive-head CI and specialist review remain separate merge gates.
This report grants no merge approval.

Resource limitation: T2 candidate terminal RSS was 1088.711 MiB versus
964.445 MiB baseline, **124.266 MiB higher**, despite a slightly lower sampled
peak. Sampling missed a small T1 peak as well. No memory improvement, exact
peak or steady-state heap claim follows; final review must assess these
observations alongside the append-latency result.

## Input, runtime and correctness

Both arms used Float64, normal enabled GC (`collect_gc=false`), default
`stable_v1`, min_periods=1, affinity CPUs [0,2], four default Tokio workers,
fixed DataFusion partitions=1 and batch size 8192. OMP, OpenBLAS, MKL, NumExpr,
vecLib, Rayon and Polars limits were 1. No scheduler experiment or selected UDF
was enabled. Recorded program/plan/project identities and actual lowered
preflight policies match across arms. The common measured Python harness was
the immutable candidate harness on both installed native wheels.
Edge limits were 1024 rows for T1/C1 and 1000 for T2, with 64 MiB per edge;
checkpoint interval was 24 hours. Default logical state budgets and the
candidate's 64 MiB process-local shared-tape quota were retained.

T1/C1 warmed 1000 rows before timing. T2 fully warmed all 10,000 entities to
60 rows each using exactly 600 physical 1000-row Data envelopes and 60 advancing
full-tick watermarks. Before-status source/rolling counters confirm those
counts in each worker. Four-digit symbol labels preserve numeric order.
Measured T2 appends then touch 1000 entities, with a new timestamp per row;
they are the original sparse append layout, not merged full-entity ticks.

The original value oracle remains in use, with rtol=atol=1e-10 and exact
sequence/input checks. In addition, each full warm output stream and every
matching append pair has an equal versioned Float64 digest. The encoding keeps
logical schema/metadata, row order, validity and raw valid 64-bit values;
it canonicalizes only Arrow chunk boundaries and excludes undefined null
payloads. It does not normalize signed zero or valid NaN payloads. Those
encoding edge cases have focused helper tests; they are not extra timing cases.

All three warm digest pairs and 90 append digest pairs match. All 180
independent append oracle checks pass with zero mismatched values. Warm and
append validation covered 1,386,880 rows across both arms; append-only rows
total 182,880. Native statuses independently confirm source/sink row counts.
Every job ended naturally, completed terminal epoch 1, had no late rows,
task/operator errors or metric overflow, and finished with zero tasks and
empty edge queues. Temporary warm directories were removed.

Append timing includes prepared Data enqueue, source/task/channel work,
watermark finality, projection, sink receipt and conversion to PyArrow. It
excludes generation, IPC gaps, validation, history warmup, startup, checkpoint
and shutdown. All excluded operations still count against the inclusive
acquisition budget. No nonterminal checkpoint or restore case was injected;
ordinary EOF/terminal completion is retained. Recovery, held-extra-snapshot
aliases and other profiles/lanes keep their direct test coverage and are not
new performance claims here.
These sub-64,000-row, 20/60-window cases do not measure entity-parallel lanes
or sorted SQL two-AVG execution.

The existing owned-process RSS helper sampled each worker tree with a nominal
20 ms sleep between polls; process enumeration/guard work adds time. These are
sampled maxima and can miss brief peaks, as T1 candidate's higher terminal RSS
demonstrates. CPU is the last sampled process user+system total, not an exact
complete-lifetime total or the CPU of timed appends alone. Each worker has
samples and a normal, reaped, OS-exit-zero receipt. There is no per-resource
confidence interval from these single worker lifetimes.

T2 candidate terminal RSS was 124.266 MiB higher despite its slightly lower
sampled peak. This is disclosed without attributing it to a tape allocation,
credit leak or memory saving. Long-running allocator retention, exact peaks
and deliberately held extra snapshots were not measured. All six processes
actually exited and no owned process remained.

Native before/after rolling metrics are retained separately from RSS and unit
allocation evidence. Over post-warm through terminal handling, T2 recorded
30,000 touched and copied entities in both arms, 30,000 numeric rows, and zero
history rows materialized. Its accumulated state-preparation wall time was
27.810302 / 8.941175 ms B/C; numeric-update wall time was
4.004867 / 12.474566 ms, and history-maintenance wall time was
104.288284 / 89.023281 ms. These are callback-lifetime deltas, not individual
sample attribution or CPU timings, and do not replace the end-to-end result.

`copied_entities` counts entity state copies, not actual tape allocations,
copied rows/bytes, quota credits or fallback events. The timed wheels expose
none of those private allocation counters. Direct unit witnesses for actual
COW allocation/credit lifetime are separate correctness evidence. The 64 MiB
process-local tape quota is not a whole-process RSS bound; Arrow history,
keys, old/new state owners and runtime infrastructure still cost memory.

T2's single recorded warm elapsed times were 49.888705 / 51.038588 s B/C.
They are included in the outer budget and preserved descriptively. They do
not establish a warmup or whole-job speedup; that was not the paired target.
