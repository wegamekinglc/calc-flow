## Observation unit and unchanged scheduled contract

The existing `stream_sql_aggregate` executable gains only an opt-in
`--snapshot-cache-case sparse|dense` mode, requiring `benchmark-internals`.
Its default seven-case inventory, v3 report format and scheduled validator's
default minimum of twenty samples/report stay unchanged. The new mode has a
distinct `calc-flow.sql-snapshot-cache-invocation.v1` schema and a narrow
`sql_snapshot_cache.selected_snapshot_row` extractor. It cannot be passed off
as a scheduled twenty-sample report; conflicting legacy sample/type/check flags
are rejected.

**One fresh native process is one statistical observation.** It warms one
operator, performs exactly twenty business appends and validates recovery.
Its primary time is the sum of twenty `SqlOperator.process_data` wall intervals
through the original collector's complete owned-Batch receipt and commit.
This includes full snapshot construction/emission, not a private raw-cache
micro-loop. Complete typed row reads, independent oracles and immutable-held-
snapshot checks happen outside those twenty intervals. Warmup and validation
are separately reported. This is a native operator/collector boundary, not a
Python/source/channel whole-job benchmark.

The twenty appends are fixed workload size, **not twenty statistical samples**.
The selected extractor returns `samples=[sum(process_data_seconds)]`.
Maintained `release_pairs.collect_case/evaluate_case` supplies **two rounds of
ten alternating AB/BA pairs per case**, twenty actual pairs total per case.
Two cases × twenty pairs × two arms means **80 fresh native processes**, with
no nested twenty plan repetitions, extra timing case or native warmup probe.
Each process's twenty raw append intervals remain in its report as diagnostics.

## Exactly two workloads

| Case   | Role    | Existing slots appended each transaction   | Input slot counts by 8192-row chunk  |
|--------|---------|--------------------------------------------|--------------------------------------|
| sparse | Target  | 9000–9999                                  | [0, 1000]                            |
| dense  | Control | sorted unique `(i * 37) % 10000`, i=0..999 | [853, 147]                           |

Both cases use the unchanged entry fixture: 10,000 closed groups, two Utf8
keys, Int64 SUM, warm value 1 and twenty 1000-row appends with increments
1..20. Account is null only at warm slot 0; other keys are
`account-{slot/100:03}` and `stock-{slot%100:03}`. Input value and stock are
non-null. The exact SQL is:

```sql
SELECT account, stock, SUM(value) AS total FROM events GROUP BY account, stock
```

Group order is the warm first-appearance order. Every output is a complete
10,000-row snapshot in [8192,1808] chunks, with exact field/schema/nullability,
default Batch metadata and all key/value rows checked. No row sorting,
changed-state/delta output, postprocessing change or new group is introduced.
The original warm snapshot stays alive through all twenty timed appends and
is checked against its original values after each append. Holding and re-reading
that snapshot does not create another emitted snapshot.

The native model and independent Python oracle hash every logical row using
the versioned `calc-flow.c1-rows.v1` encoding: row count as little-endian u64,
ordered nullable-key validity bytes and length-delimited UTF-8, then valid
Int64 value bits. Undefined null payload bytes are not hashed. Input hashes,
all twenty full output hashes, held-warm hashes and metadata must agree.
Default metadata is `{"source":"", "sequence":0, "attributes":{}}` for every batch.

## Recovery and honest phase counts

After the primary workload, capture the existing compact checkpoint outside
primary timing. Validate layout/accounting 3, group-state Arrow rows/columns,
logical input counts and a canonical checkpoint SHA. Restore a new cold
operator, emit one unchanged snapshot using an empty Data batch, then append
one value-1 row to original slot 0 and validate the resulting full snapshot.
This is the existing untimed recovery correctness contract for the same case,
not another timing workload or checkpoint matrix.

| Phase                       | Input rows                 | Output rows   | Emitted snapshots   |
|-----------------------------|----------------------------|---------------|---------------------|
| Warm                        | 10000                      | 10000         | 1                   |
| Twenty primary appends      | 20000                      | 200000        | 20                  |
| Cold restore + continuation | 1 (empty0 + continuation1) | 20000         | 2                   |
| All phases                  | 30001                      | 230000        | 23                  |

Warm plus primary alone is 30,000 input/210,000 output rows. The captured
checkpoint describes those 30,000 original input rows, not the later restored
continuation. Held-warm revalidation checks 200,000 logical rows but emits none; internal
comparison and hashing may visit buffers more than once.
Primary throughput uses 20,000 appended input rows; its metadata/identity must
not claim 30,000 or 30,001 timed input rows. Recovery counts/hashes and total
counts are explicit separate fields. The normalizer rejects incomplete,
miscounted, bit/hash-mismatched, non-finite or metadata-inconsistent reports.
