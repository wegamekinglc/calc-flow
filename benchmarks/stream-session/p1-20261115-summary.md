## Where the remaining cost is

Case 1 phase attribution (candidate session, p50): forced GC — Python
argument handling 18.9 µs, native call 126.9 µs, result assembly 7.0 µs;
normal GC — 10.9 / 75.0 / 5.1 µs. The bridge (argument handling, export,
`pa.Table` assembly) is not the main cost.

In-process diagnostics on the candidate wheel
(`target/stream-session-p1/diag-scripts/`, not committed):

- a no-op session call (equal watermark: binding, GIL release, current-thread
  `block_on`, drain loop) costs 0.46 µs;
- the same 1-row dual-SMA push in a tight loop costs 18.6 µs p50 without a
  forced collection and 175 µs with one (pure column projection: 12.0 vs
  106 µs);
- so the cost depends on cache state: hot ≈ 19 µs, after harness IPC and
  validation ≈ 90 µs, after `gc.collect()` ≈ 153 µs. TA-Lib moves from 5.6 to
  39 µs under the same forced collection.

Conclusion: the caller-thread session removes the runtime bridge (3.5–5.4×
on small appends, 1.9× at 6,400 rows, no runner regression), but the existing
async operator path touches enough memory and code per call that its latency
depends heavily on cache state. The remaining cost is inside the native
operator dispatch (rolling data and finalization callbacks, contexts,
per-call allocations and large async state machines), which is the subject of
plan P2 (allocation-free rolling kernels) and the synchronous operator trait
of plan §4.1. A per-call allocation and footprint budget should be added to
P2's acceptance alongside the warm-loop and harness latencies.

## 2026-11-19 inline runner and NumPy evidence

Raw reports and build provenance are committed alongside this summary:
[p1-inline-performance.json](p1-inline-performance.json),
[p1-numpy-native-types.json](p1-numpy-native-types.json), and
[p1-numpy-native-types-build.json](p1-numpy-native-types-build.json).

- The inline runner comparison used 30 AB/BA pairs per case. One-row dual-SMA
  measured 0.976x (95% CI 0.934–1.137), and 6,400 rows × 64 entities measured
  0.962x (0.881–1.031). Both are inconclusive, not confirmed regressions or
  speedups. The comparison elapsed 4.154 seconds; build cost is separate.
- The NumPy acceptance case used five warmups and 30 timed samples for one
  prepared Float64 row and `rolling_mean(window=2)`, timed from
  `_StreamSession.push` through `NativeArray.to_numpy()`. It measured **2.885
  µs p50**, passing the ≤5 µs gate. The implementation and summary landed in
  `cf75ea79`; the raw report records the exact source and wheel hashes. No
  baseline speedup is claimed because the baseline rejects ndarray inputs.
