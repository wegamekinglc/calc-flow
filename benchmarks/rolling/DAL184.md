# DAL-184 incremental rolling comparison

This informational benchmark compares the current native `RollingOperator`
path produced by symbolic `ts.*` declarations with the previous DataFusion SQL
window-function path. Both plans execute in the same Python process over the
same immutable Arrow input and emit the same ordered columns. The corresponding
user-facing workflow is
[`14_symbolic_incremental_rolling.py`](../../examples/14_symbolic_incremental_rolling.py).

## Workload and semantics

| Parameter             | Value                                                                |
| --------------------- | -------------------------------------------------------------------- |
| Input                 | deterministic interleaved per-symbol quotes, seed `20260822`         |
| Standard size         | 99,968 measured rows (100,000-row scale aligned to 64 entities)      |
| Entity count          | derived identically by `quote_workload` (64 in the recorded run)     |
| Windows               | 20 and 60 entity rows                                                |
| Step                  | one output per input row                                             |
| Features per window   | mean, sample standard deviation, sum, minimum, maximum               |
| Minimum periods       | 1 valid sample; sample standard deviation additionally requires 2   |
| Boundary              | current row plus at most `window - 1` preceding rows in its entity   |
| Nulls                 | every 29th position per entity is null                               |
| Null policy           | exclude null samples; emit null when no valid sample exists          |
| Floating comparison   | `rtol=1e-10`, `atol=1e-12`, matching null masks, `equal_nan=True`    |
| Warm-up               | one untimed execution per implementation                             |
| Formal repetitions    | 30 alternating same-process pairs                                    |
| Summary               | median latency; throughput is input rows divided by median latency   |
| Timed boundary        | synchronous `BatchExecutionPlan.execute` through materialized output |

Correctness is checked before the first timed sample. The incremental plan is
run first on even repetitions and the SQL plan first on odd repetitions to
reduce order bias. `pytest-benchmark` also times the combined pair for suite
integration; the per-implementation comparison comes from the 30 alternating
samples stored in the JSON `extra_info`.

## Reproduce

Build both plans into the same release-mode native extension, then run only the
focused scenario:

```bash
uv sync --extra benchmark --extra dev
uv run maturin develop --release
mkdir -p target/benchmark-results
CALC_FLOW_BENCHMARK_PROFILE=release \
  CALC_FLOW_BENCHMARK_SCALE=standard \
  JAX_PLATFORMS=cpu \
  uv run pytest \
  benchmarks/test_rolling_comparison.py::test_incremental_rolling_vs_sql_window \
  -q -s --benchmark-only \
  --benchmark-json=target/benchmark-results/dal-184-rolling.json
```

The JSON records OS, architecture, CPU, logical CPU count, Python, NumPy,
PyArrow, process/peak RSS, scale, row/null counts, window/step parameters,
warm-up/repetition counts, raw paired samples, both summaries, relative change,
and whether the incremental median regressed against SQL. Peak RSS is a
whole-process high-water mark, not memory attributed to one implementation;
the existing harness does not expose portable per-plan CPU or allocation data.

## Warm-state append comparison

`test_rolling_warm_append.py` measures the workload that exposes the native
operator's retained state. Every sample creates a new public
`StreamingRunner`, sends the same seed table, and advances a source-provided
watermark until the sink has materialized all seed output. The source then
stops at an asynchronous gate before emitting an empty probe batch after the
seed watermark. While that gate is closed, the benchmark waits for rolling to
report exactly one input batch and a positive cumulative processing duration,
which acknowledges the seed data handler's completion. It then releases the
probe and requires both at least two input batches and a strict increase in
cumulative processing duration. The runtime increments input batches before
calling `process_data`, but records processing duration only after that await
returns, so the second condition is the post-handler completion
acknowledgement. Because an operator processes its input stream serially, the
preceding watermark is also complete before the timer can start. Compilation,
deterministic input construction, seed processing, the empty probe, warm-up,
and correctness checks are outside both timers.

The native timer starts immediately before releasing the delta gate and stops
after the sink has converted and collected exactly the delta output. The SQL
timer executes one reused, precompiled DataFusion plan over the complete
`history + delta` table through Arrow collection. This is therefore an
end-to-end public streaming append measurement: it includes Python
source/sink callbacks, async scheduling, watermark propagation, and Arrow
materialization. It is not a pure Rust rolling-kernel microbenchmark.

Each standard case uses one untimed warm-up and five measured samples. The
measured order alternates between native and SQL. A fresh runner is seeded for
every sample, so history never grows across repetitions. Runtime assertions
and JSON evidence require all of the following:

- seed completion precedes the native timer;
- before probe release, rolling has completed the seed data handler;
- after probe release, rolling's input count and processing duration both
  increase before timing, acknowledging the probe handler's return;
- the source emits seed and delta exactly once;
- native timed output contains exactly `delta` rows;
- SQL output contains exactly `history + delta` rows;
- every sample begins with the same 99,968-row logical history;
- SQL's final delta rows and native output match by entity, event time,
  sequence, column order, null mask, and floating value.

The standard matrix fixes 64 entities and five statistics (mean, sample
standard deviation with `ddof=1`, sum, minimum, and maximum). Each case has
one row window rather than mixing multiple windows. Null and boundary rules
are identical to the cold comparison above.

### Reproduce warm append

From a clean checkout, unset an active Conda prefix so Maturin binds the uv
environment's Python, build the native extension in release mode, then run the
exact benchmark node:

```bash
env -u CONDA_PREFIX uv sync --extra benchmark --extra dev
env -u CONDA_PREFIX uv run maturin develop --release
mkdir -p target/benchmark-results
env -u CONDA_PREFIX \
  CALC_FLOW_BENCHMARK_PROFILE=release \
  CALC_FLOW_BENCHMARK_SCALE=standard \
  JAX_PLATFORMS=cpu \
  uv run --extra benchmark pytest \
  benchmarks/test_rolling_warm_append.py::test_warm_state_append_vs_sql_full_recompute \
  -q -s --benchmark-only \
  --benchmark-json=target/benchmark-results/dal-184-warm-standard.json
```

Use `CALC_FLOW_BENCHMARK_SCALE=overhead` for the fast CI/development profile.
It preserves all 12 `(delta, window)` combinations but reduces history to the
active scale and measured repetitions to one. The standard profile is the
recorded 99,968-row, five-sample contract.

### Warm-state measured summary

Recorded on 2026-09-04 on the same WSL2 host and release build described
below. The command completed all 12 cases in 68.27 seconds. `Speedup` is
`SQL median / native median`. Native throughput divides delta rows by native
append latency; SQL throughput divides all `history + delta` rows by SQL
latency. Those throughput values intentionally describe different work and
must not be presented as a like-for-like throughput percentage.

|    64 |     60 |      3.173 ms |         146.432 ms |  46.15x |              20,169 |          683,131 |
|    64 |    252 |      6.174 ms |         140.507 ms |  22.76x |              10,365 |          711,934 |

|   640 |     60 |      4.386 ms |         147.037 ms |  33.52x |             145,920 |          684,235 |

|   640 |   1024 |     17.361 ms |         123.559 ms |   7.12x |              36,864 |          814,251 |

All five-sample medians favor warm native append. The advantage is largest
when delta is small relative to retained history, as expected for
`O(delta)` append versus `O(history + delta)` full recomputation. Native
end-to-end latency still increases with a wider retained window, especially
for a 64-row delta; this benchmark records that cost rather than claiming the
public runner path is constant with respect to window size. These are
single-machine observations, not general performance guarantees.

## Cold full-batch measured summary

Recorded on 2026-09-03 from the DAL-184 implementation worktree in release
mode:

| Implementation       | Median time | Throughput       | Total across 30 samples |
| -------------------- | ----------- | ---------------- | ----------------------- |
| Native incremental   | 161.616 ms  | 618,554 rows/s   | 4.923 s                 |
| SQL window functions | 248.681 ms  | 401,992 rows/s   | 7.507 s                 |

The native incremental median latency was 35.01% lower and its median-derived
throughput was 53.87% higher. No regression was observed. This benchmark is
informational and intentionally defines no absolute pass/fail performance
threshold.
