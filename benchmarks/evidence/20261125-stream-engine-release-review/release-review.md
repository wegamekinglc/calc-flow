# 2026.11.14 至 11 月 25 日 main 的流执行路径审阅

发布版为 `7012b5b409553df04e29e6d7f9a11abf919cbf93`，核对远端 main 为 `72072c1dc6c0874b79ccd8ce78103c97caec623d`。本次以生产编译路径为准，分别考察原生 Rust 回调、Rust 运行图、Python 公开作业。不同输入大小、线程数、输出语义和计时边界各自比较。

## 对应版本的测量

- **ASOF，原生 Rust。** 每侧 10 万行、64 键、每侧两个输入批、一个最终水位。未插桩回调 p50/p95 从 7.020/7.698 升至 12.288/13.342 ms。按插桩后每次回调的互斥耗时均值计算，增加 5.343 ms，其中 Arrow 输出贡献 +4.772 ms（89.3%），左侧提交 +1.012 ms，右侧淘汰 +0.320 ms，匹配 −0.949 ms。接纳输入 p50 反而从 16.981 降至 15.351 ms。两组分别做了两轮、每轮十对，核对所有 10 万行及最终状态。[分阶段数据和校准](https://github.com/wegamekinglc/calc-flow/blob/d0fee918f7277557bd068d3da285dfaa44d2a152/benchmarks/evidence/20261125-asof-watermark-phases/native-phase-summary.md)
- **ASOF，Python 公开流。** 4 线程独立实验的每侧百万行场景中，同一次作业内各 finalize 回调总耗时的 p50 从 17.484 升至 65.649 ms，Arrow 段从 0.029 升至 29.481 ms；匹配段的两轮配对增量为 +10.32 和 +9.49 ms。这里计量 Python 作业内的 Rust 回调，不能由此推算 PyO3 转换占比。发布版原生多记录样本进入 gather worker，公开流的数据布局能触发不同的输出路径。
- **历史参照。** 定时任务 `85af0b53` 的四线程百万行公开流中，发布版→该旧候选的 p50 分别为平均值 39.154→131.163 ms、静态 Join 80.251→120.639 ms、ASOF 109.647→656.164 ms，三者均确认回退。同批 GroupBy 38.455→37.699、区间 Join 691.396→556.055 ms 均为 inconclusive。表中 61 项 regression 均指该任务的候选版本；其 Rust 分片使用该提交的第一父提交作基线。其余各节注明的阶段实验也各有自己的基线。[定时任务与分片](https://github.com/wegamekinglc/calc-flow/actions/runs/45371854358)

## 小阶段顺序

1. ASOF 只改已定位的 Arrow 输出，再对照封存的原生回调及 Python 公开入口。分别保留 handler、整作业与状态指标。
2. 对最新百万和千万行累计 average 的 1T/4T 回退，先用相同数据核对实际内核分派，再区分调度、实体路由、数值状态更新和输出。专门审阅不应归入 SQL 分组聚合。
3. 静态 Join 与区间 Join 各自测通用 schema、保持匹配数和预算；GroupBy 以稀疏热更新对照全量输出。过滤、窗口关闭与检查点各在对应证据出现后进入独立小 PR。
