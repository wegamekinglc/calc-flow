# ASOF 水位处理与 Arrow 输出分段复测

比较 11 月 14 日发布提交 `7012b5b4` 和合入 #741 的 `main` 提交 `ea7a21ce`。每组两轮，每轮十对正式样本，另有四次预热。单位为毫秒，各行独立取 p50、p95。平均差值来自同对样本，正数表示 main 用时增加。

原生 Rust 每侧 10 万行、64 键、两批固定宽度数据，计量一次水位回调。公开 Python 安装包每侧 100 万行、64 个字符串键、四线程。Python 分段是同一作业中 Rust 回调的总和，含预水位及 EOF 回调，公开总时钟从输入就绪到最终 Arrow 表交付。两个入口各自对照发布版。

最初对照的 main 为 `72072c1d`。在每侧十万行的 Rust 单次水位中，Arrow 平均多用 4.772 ms，约占总差距 5.343 ms 的 89.3%。在每侧一百万行的独立安装包中，二十对样本的作业内累计回调平均多用 48.601 ms，其中 Arrow 多用 29.376 ms（60.4%）、匹配多用 10.284 ms、左侧提交多用 8.684 ms、右侧淘汰多用 0.234 ms。每个环境分别以其发布版为基线。下文复测包含后续完整列共享、整段左侧提交和输入处理修复。

## 本轮定位

按已安装 Python 作业中所有水位回调的配对均值，Arrow 总差值为 +10.332 ms。其中差值最大的子段为输出预算（+8.670 ms）。

相同夹具的无插桩整作业平均差为 +56.855 ms。回调分段来自另一组独立配对采样；整作业还包含接纳、调度与最终表交付。

在这个负载上，匹配和就绪判断平均多用 11.348 ms。输出预算占 Arrow 差距的 83.9%。右侧淘汰的全作业累计差仅 +0.072 ms；仅统计发出结果的回调会漏掉其他水位和 EOF 处的淘汰。

下一小步检查有序探测对同一键的前驱和下一条右记录时间的重复读取。Polars 的 backward 状态跨探测保留已命中位置和扫描位置。calc-flow 还需验证同时间的最大序列、容差边界和间隔很大的时间跳跃。[Polars 源码](https://github.com/pola-rs/polars/blob/22a147de3d2bb2e44b97338a2510816c7105c9f2/crates/polars-ops/src/frame/join/asof/mod.rs#L71)

Python 对照按序列核对全部行和值，并验证最终状态。这里的数值不能用来推断交付的物理顺序或 Python 绑定自身的开销。

输出预算代码在计算保留字节数时曾按 run 建立逐行索引，再根据索引计算投影列大小。#745 对确实完整覆盖的有序新 run 复用列长度与有效位图计费，消除了这个索引向量。多 run、空值、重复投影的独立分配测试中，两个预算计算在父提交分配 263,360 字节，候选达到 2,048 字节以内的上限。普通 Rust 和安装包的效果另有产品对照。[实现与测试](https://github.com/wegamekinglc/calc-flow/pull/745)

发布版输出预算段包含末级预算预留、相关配置检查、一次 Tokio 主动让出及取消检查；构造匹配引用时的部分计费仍计在匹配段。列处理计父任务等待 gather worker 的墙钟。发送单列。每个回调都验证阶段闭合，四个 Arrow 子段之和等于该回调的 Arrow 总时长。
