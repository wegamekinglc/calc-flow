# 跨库性能优化：原开发方案

本文整理 2026-09-10 制定的最初开发方案，保留原目标、核心约束、实施顺序和验证设计。
它不是实施结果或验收通过记录。最终交付行为与已知限制以
[CHANGELOG](../../CHANGELOG.md) 和[当前指南](../README.md)为准；
本文件不包含后续迭代、实验日志或审查过程。

## 1. 问题与范围

主要调查方向包括 UInt64 过滤表达式的 Decimal128 类型提升、Native rolling 的
输入处理与实体路由、状态准备、历史保留和输出成本，以及完整窗口 SQL SMA 查询中
`COUNT` 守卫未被 AVG 重写覆盖的问题。单独加快算术或减少等待，不能证明完整应用
边界的执行更快；输出、最终性、恢复和资源约束必须同时保持。

原方案包含 P1–P7 七项工作。具体数据结构和算法是候选手段，不是预先指定的实现。
既有跨库耗时只作为调查线索：来源不明的历史二进制不能充当发布回归基线，
也不据此承诺达到某个毫秒值或追平 Polars、TA-Lib。

优化继续使用现有 Python 应用 API 和 Rust/DataFusion 表运行时，不引入新表引擎、
Batch 类型或可执行配置对象，不改变数值默认配置、数据重放或 sink 交付保证。
不得通过放宽容差、扩大队列或减少实际输出工作制造收益。
Studio 仅在所选公开诊断或配置接口确实影响其契约时同步调整。

## 2. 必须保持的核心不变量

1. **FB1：应用与表契约。** Arrow 输入不可变，schema、nullability、metadata、
   逻辑输出名和行身份保持；Python 异步结果继续拥有并清理资源。SQL 输出仍创建新的
   行血缘，不把物理排序证明当成新增的 Python 时间顺序声明。
2. **FB2：完整与部分窗口。** 原 SMA20 和双 SMA 查询均保留完整 20 行慢窗口守卫；
   十行输入仍没有完整窗口结果。已有部分窗口 warm workload 单独报告，不能代替
   完整窗口重写的验证。保留各算子的 `min_periods`、frame 和值处理策略。
3. **FB3：数值配置。** `stable_v1` 仍为默认，`stable_v2` 仍为显式且参与指纹的
   preview。保留运算顺序、既有有限值容差、count 门槛、null/NaN/正负无穷分类、
   add/remove、refold/rebase 触发及恢复重建。仅输出 mean 不代表可删除 M2 或
   改用 sum/count；必须保留近溢出有限窗口的 West mean 行为。
4. **FB4：顺序与最终性。** 保留输出规范顺序、实体内递推顺序、sequence/event-time
   平局处理、允许迟到边界，以及 late Drop/Error 先于重复校验的错误次序。
   输出和下游 watermark 不得越过更早身份或最终性尚未完成的工作；混合路径、
   空批次、多 RecordBatch 和 EOF 行为保持。
5. **FB5：失败与提交。** 畸形 envelope 或关闭坐标溢出须在接受状态改变前拒绝。
   rolling 状态、历史、递推计数和输出序列只在原成功 emission 边界允许时推进。
   输出失败、取消及 restore 失败保持原重试和原子性；已被普通 sink 接受的块不可
   撤回，不能据此承诺新的 exactly-once 交付语义。
6. **FB6：状态兼容。** 保留 project-v3、managed manifest v3、rolling 列式 writer
   layout 3，以及既有声明允许的 legacy layout 1/2 恢复。未变声明的配置、数值、
   kernel 和状态 schema 身份保持有效。reset 清空全部自有状态，成功 restore 替换
   状态，非法或不兼容 restore 不得部分提交。
7. **FB7：资源有界。** 保留精确边行数/字节预算、超大行错误、checked 计数、取消
   所有权和有界在途工作。小 Arrow slice 不得长期保留整段历史输入；活跃实体/窗口
   状态、尚未最终化的输入、来源历史及收集输出必须分开核算。

## 3. P1–P7 工作目标

### P1：UInt64 过滤表达式

在能够证明 Boolean 结果、null 和错误语义等价的上下文中，避免目标 UInt64
取模过滤的 Decimal128 算术。允许有严格条件的原 SQL 谓词重写；不能只新增一个
更快的 benchmark 查询，就声称原查询获得了引擎优化。

覆盖 0、null、`2^63 - 1`、`2^63`、`2^64 - 1` 和除数边界附近的值。
负数、越界字面量、零除数、不同类型和其他未证明形状保留原行为或回退。
保留原 `sequence % 4 = 0` 比较；显式类型诊断变体须有独立名称，不能混同于
同查询的版本收益。位掩码等替代算法只在语义已证明时采用。

### P2：Native 阶段归因与内存观测

区分输入校验、顺序证明、实体解析、受影响状态准备、数值更新、历史维护、
Arrow 输出、预算/分块准备及发送等待。明确 counts、bytes、nanoseconds 的单位，
说明区间归属和嵌套关系；互斥阶段不得重复收费，包含子阶段的父计时须标明。

通过原 native job 边界提供有界诊断事实，保留已有 metric 的名称和含义。
区分累计值与单次差值、Data 与 watermark 工作、终态快照与计时结束瞬间，
明确失败和取消的统计语义。

对代表性 workload 采集 CPU/调用栈样本、实际分配次数和字节、峰值及保留内存。
`Vec` 容量估算或逻辑状态字节不等于分配测量。昂贵插桩与普通计时分开，说明工具
能力和缺项，测量观测开销；诊断记录不得无界增长或持有输入行、Python 对象。

### P3：实体键、ID、历史与状态准备

分别处理三个成本来源：

- 减少重复/新实体的 key ownership、ID 遍历和复制。nullable、多列键及不同批次的
  dictionary 编码保持值身份；批内字典索引不能作为持久实体身份。
- 减少尾部历史处理，仍保留回退和 checkpoint 重建所需历史及递推元数据。
  覆盖批量小于/大于窗口、多窗口、稀疏追加和活跃实体集合变化，保留量不得随
  已最终化的全部历史持续增长。
- 减少受影响实体的准备和复制，避免稀疏追加承担未触及历史的成本，同时保持 FB5。
  必须保留的复制应说明原因；除整条路径耗时外，也核对复制和转换工作量。

借用键、紧凑 ID、列式尾部和减少状态复制均需要各自的行为及内存证明。

### P4：有序 SQL rolling 路径

利用 SQL 物理计划证明的 partition/order 属性减少通用实体路由；无证明时回退，
不得信任未排序输入。每个物理分区及每次执行拥有独立的正确 rolling 状态。

实体跨 RecordBatch 时保留状态，在实体、分区和执行边界正确切换或重置。
覆盖 null 实体键、相同时间戳的 sequence 平局、空批次、多窗口，以及经物理排序
后的原无序输入。用计划与路径断言证明实际采用了目标路径，不删必要 sort，
也不把未验证的 sort 次数或 oracle 的隐藏排序当成优化依据。

### P5：数值状态与校验/预算路径

结合 P2 观察和对抗性数值用例，评估 mean-only 与共享输出需要哪些状态。
采用特化必须在实时更新、回退和恢复中证明 FB3；保留必要状态是有效设计结论，
但不能因此省略校验/预算优化。

仅对已证明的适用路径减少重复校验或预算处理，保留精确逐行收费、溢出检查、
envelope 原子性、迟到优先级和错误身份；其他类型或未证明的整批界限使用原细粒度路径。
覆盖定长/变长数组、逻辑 slice offset、validity bitmap、多字节字符串、空批次、
恰好适配预算、超出一个字节的行及接近上限的计数。宽松内存估算不能替代精确边收费。

### P6：完整窗口 COUNT/AVG 重写

覆盖未修改的 SMA20 与 SMA5-minus-SMA20 查询中的兼容有界 `COUNT(column)` 和
`AVG(Float64Column)`。保留别名、输出顺序/schema、DataFusion COUNT 的类型和
nullability，以及全 null、NaN、正负无穷行为。

只有 source/frame/partition/order 和语义一致时才能共享计数。SQL COUNT 统计
非 null 值，不能未经证明替换为 native numeric valid-count，尤其不能忽略 NaN 区别。
不同窗口按语义保持独立。

保留 candidate/rewrite/fallback 指标及显式关闭重写的对照。不支持的聚合、COUNT
形式、FILTER、DISTINCT、cast、frame、null-treatment 或 order 形状回退到 DataFusion。
说明支持子集；不要求增加原先不支持的 `COUNT(*)`。P4/共享路径改善后，再验证
完整窗口端到端收益；部分窗口收益不能代替这一验证，单/双 SMA 和小输入成本分别报告。

### P7：小请求融合或实体并行

依据 P2/P3 的归因，选择至少一种小请求算子融合或显式实体并行路径；两者不要求同时
实现。仅调 Tokio 线程数、watermark 频率、batch 大小或队列容量不构成该项实现。

融合须保持输出名/schema/行血缘、顺序、算子错误上下文、生命周期、最终性、
状态所有权、project 身份和恢复；不支持的组合或时间转换保留必要执行边界。

实体并行须证明实体内串行递推、确定性合并、watermark/checkpoint 对齐、在途工作
有界及取消/清理/恢复行为。覆盖单热点实体、均衡、偏斜、慢 sink 和单 lane 失败；
调度池大小本身不能证明实际并行。

保留串行/未融合对照，比较无插桩 P50、描述性 P95/P99、分配、峰值内存及首次输出/
最终性延迟；中位数改善不能证明尾延迟安全。

## 4. 原定验证原则与性能目标

以下为最初计划的验证标准，不是最终完成情况。

1. 使用干净、隔离构建和导入目录的 release 基线/候选。记录源码、harness、lockfile、
   编译器/profile/features、wheel/native 身份、实际加载产物及机器/亲和/线程配置。
   debug 或来源未知的二进制不能建立性能结论。
2. 两侧使用相同 workload 和声明的计时边界，分别报告 ready-runner 空状态、warm
   append 与 SQL。不得以隐藏预加载、扣除 startup、提前停止、减少 Arrow 物化或
   将真实生产工作移出计时来制造收益。
3. 每次输出在计时之外校验 schema、行身份、validity、NaN/无穷分类和既有有限值容差。
   跨库 oracle 的规范化须明确，不得削弱跨版本兼容性测试。
4. 沿用两轮全新 worker、每轮十对 AB/BA 和精确配对中位数区间。原增益条件是两轮
   candidate/base 百分比变化区间上界均低于 −5%；+5% 回退规则和全部样本保持。
   不重试筛选通过、不删离群值；`inconclusive` 不是增益或性能等价证明。
5. 原目标：P1 在明确的 1M 或 10M 行优化比较中达到 `improved`；P3/P5 在至少两个
   不同 batch/entity 设置中达到 Native `improved`，其中包含 64,000 行/64 实体，
   并分别报告冷态和热态；P4/P6 在 1M 或 10M 行完整窗口双 SMA 上达到 `improved`，
   单 SMA 另有无回退证据；P7 在预先声明的小请求或实体并行目标上达到 `improved`。
6. 补充归因/敏感性子集覆盖 B=1,024/8,192/64,000/256,000、E=1/64/1,000、
   W=1/5/20 及更大窗口、稀疏和偏斜追加；不要求完整笛卡尔积。warm 历史包括
   64,000 和 1,024,000 行，append 包括 1、64、64,000 行。不同维度不混为同一组样本。
7. P50/P95/P99 均附样本数。原 P7 尾延迟设计要求每个选定场景至少 1,000 次追加，
   覆盖至少三组全新 worker 对，预先固定配置与分位数方法。缺少合适的不确定性分析
   时分位数仅作描述；CI 中位数门禁不能代替尾延迟验证。
8. 区分分配观测、RSS、输入所有权、pending rows、数值/历史状态与收集输出。
   相同实体/窗口下，已最终化历史增长不得造成 retained rolling state 持续增长。
   开销比较使用相同插桩；原方案要求 telemetry 不造成已确认超过 5% 的默认路径回退。

验证覆盖 UInt64 全域、nullable Float64、极值/抵消、W=1/W>N、跨批实体键、
迟到与错误次序、分块提交、reset/restore 及 base 产生的兼容 checkpoint。
保留失败、取消和不确定结果，不把缺项改为通过。

## 5. 原实施顺序

1. **C0：契约和基线。** 确认不变量、风险、既有测试与 workload 身份；先记录聚焦
   行为失败，区分计划中的检查和实际结果。公开诊断/配置变更先核对接口兼容性。
2. **C1：P1 与 P2。** 分别完成过滤优化及 Native 观测，取得阶段/分配依据后选择
   P3/P5/P7 的目标，避免先挑有利结果再定义目标。
3. **C2：P3。** 分别处理 key/ID、历史及受影响状态，验证顺序、回滚、恢复、
   保留内存和实际复制工作，再比较代表性冷态/热态 workload。
4. **C3：P4 与 P5。** 完成有序 SQL 路径和校验/预算优化；对数值特化作出有依据的
   保留或采用决定，不借性能改动迁移默认数值配置。
5. **C4：P6。** 在共享路径证据具备后扩展 COUNT/AVG；对原完整窗口查询分别启用/
   关闭重写，核对 NaN/非 null count 差异、不支持形状和独立 oracle。
6. **C5：P7。** 实施选定的融合或实体并行路径，验证生命周期、偏斜、单 lane/
   输出失败及有界资源，再按固定设计检查中位数、尾延迟和内存。
7. **C6：整理。** 同步当前使用与性能指南、诊断示例和生成契约；逐项区分行为结论、
   性能结果与未完成事项，进行必要的最终代码审查。
8. **C7：提交与问题处理。** PR 使用 `Summary` 和 `Test plan`，对最终提交处理
   实际 CI、覆盖率、回归、静态分析及审查问题。旧提交的通过不能自动转移到新代码，
   pending/cancelled/absent/inconclusive 不当作绿色；合并和发布另需明确授权。

本地选择改动直接相关的最小测试和必要格式/lint/契约检查，不为方案文档构建 native。
完整跨平台、服务支持的覆盖率、安全和常规性能矩阵由 CI 承担；原 Rust/connector
联合 90% 及 Studio backend 85% 覆盖率要求保持。性能执行与构建、测试、剖析隔离，
数值正确性通过和代码位置链接均不能单独证明性能目标完成。
