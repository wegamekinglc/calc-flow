# Calc Flow v0.2 Refactor Plan — DataFusion-First

## Summary

Calc Flow will become a clean-breaking v0.2 release built around:

* an immutable batch envelope over Arrow and Array API payloads;
* Apache DataFusion as the only tabular query and calculation engine;
* NumPy and JAX as optional array engines;
* a compiled DAG runtime with reliable data flow and checkpoints;
* trusted, registered, vectorized UDFs;
* versioned pipeline configuration files;
* a local FastAPI and React visual editor;
* contract, property, recovery, browser, and benchmark test suites.

Remove `PandasEngine`, `PolarsEngine`, the generic `DataFrameEngine` hierarchy,
and direct pandas/Polars dependencies. The project will not promise pandas or
Polars dataframe compatibility.

Generic objects may still be ingested when they expose standard Arrow C Stream
or DataFrame Interchange protocols. This is protocol interoperability, not
pandas/Polars support.

The refactor addresses these current limitations:

* the documented `Batch` class does not exist;
* `RecordBatch` handling differs between engines;
* `Pipeline` claims to be a DAG but is linear;
* `MicroBatchRunner.batch_size` is unused and outputs are discarded;
* checkpoints assume replayable sources and unversioned JSON state;
* array expressions use Python `eval`;
* `Context` is disconnected from operator execution;
* no serializable graph, UDF registry, benchmark suite, or web API exists.

## Target Architecture and Public Interfaces

### Immutable batch model

Introduce:

```python
@dataclass(frozen=True, slots=True)
class Batch:
    payload: pa.Table | ArrayApiArray
    metadata: BatchMetadata

    @classmethod
    def table(
        cls,
        data: pa.Table | pa.RecordBatch,
        *,
        metadata: BatchMetadata | None = None,
    ) -> Batch: ...

    @classmethod
    def from_tabular_protocol(
        cls,
        data: object,
        *,
        metadata: BatchMetadata | None = None,
    ) -> Batch: ...

    @classmethod
    def array(
        cls,
        data: ArrayApiArray,
        *,
        metadata: BatchMetadata | None = None,
    ) -> Batch: ...
```

`BatchMetadata` contains:

* `batch_id: str`;
* `sequence: int | None`;
* `source_id: str | None`;
* `cursor: JSONValue | None`;
* `event_time: datetime | None`;
* `watermark: datetime | None`;
* immutable JSON-compatible attributes.

Behavior:

* Preserve `pa.Table` directly.
* Convert `pa.RecordBatch` to a single-table `pa.Table` without copying Arrow
  buffers.
* Accept protocol-based inputs through `__arrow_c_stream__` or `__dataframe__`,
  using PyArrow interoperability.
* Do not import pandas or Polars while adapting protocol-compatible objects.
* Document that protocol conversion may copy when the external producer cannot
  expose compatible Arrow buffers.
* Validate array objects through `__array_namespace__`.
* Never silently move arrays between NumPy and JAX.
* Treat payloads as read-only and require operators to return a new batch when
  data changes.
* Preserve metadata unless an operator explicitly produces updated metadata.
* Reject table-to-array transitions unless the graph contains an explicit
  adapter node.

### DataFusion table runtime

DataFusion becomes a required core dependency alongside PyArrow. There is no
configurable dataframe backend.

Introduce a `DataFusionRuntime` owned by each execution run:

```python
runtime = DataFusionRuntime(config)
result: Batch = runtime.sql(
    query,
    inputs={"orders": orders_batch, "customers": customers_batch},
)
```

Responsibilities:

* Construct one `SessionContext` per run or worker.
* Register trusted UDFs once when the context is created.
* Register input Arrow tables under unique execution-scoped names.
* Execute SQL or DataFusion expression plans.
* Return a canonical `pa.Table` inside a `Batch`.
* Preserve or deliberately merge input metadata.
* Collect DataFusion execution-plan metrics for `RunResult`.
* Dispose of run-scoped registrations after execution.

Provide two table calculation operators:

* `ExpressionOperator` for projection, calculated columns, filtering, and
  built-in function expressions;
* `SqlOperator` for multi-input joins, aggregations, windows, sorting, and
  general `SELECT` queries.

Both compile to DataFusion logical plans. They do not execute through pandas,
Polars, or Python `eval`.

Security and validation:

* Limit pipeline SQL to a single query/`SELECT` plan.
* Reject DDL, DML, multi-statement SQL, filesystem table registration, and
  extension loading from project configuration.
* Quote generated table and column identifiers.
* Validate referenced input ports before query execution.
* Validate output Arrow schema when the node declares one.
* Use `SessionConfig` for DataFusion execution batch size, partition count, and
  optimizer settings. These settings are distinct from source batching.

Remove:

* `DataFrameEngine`;
* `PandasEngine`;
* `PolarsEngine`;
* pandas and Polars dependencies;
* dataframe backend selectors in Python configuration and the UI;
* cross-dataframe-engine equivalence tests.

### Array runtime

Retain `NumpyEngine` and `JaxEngine` as optional extras.

Change them to consume and return `Batch` objects with array payloads. Replace
Python `eval` with a cached AST compiler that allows only:

* literals;
* arithmetic and comparisons;
* indexing and slices;
* approved names;
* approved `xp` functions;
* explicitly registered array UDFs.

Reject attribute traversal, imports, comprehensions, lambdas, arbitrary calls,
and builtin access.

NumPy and JAX remain separate backends because they have meaningful ownership,
compilation, and synchronization differences. Backend conversion requires an
explicit graph adapter.

### DAG and execution contracts

Replace the internal operator list with a compiled graph:

```python
pipeline = (
    Pipeline("example")
    .add_node("source", source_operator)
    .add_node("calculate", expression_operator)
    .connect("source", "calculate")
)

plan = pipeline.compile()
result = plan.execute({"input": batch})
```

Interfaces:

* `Operator.process(inputs, context) -> Mapping[str, Batch]`;
* named and typed input/output ports;
* `Pipeline.add_node()` and `Pipeline.connect()` for graph construction;
* `Pipeline.then()` and `Pipeline.add()` as linear sugar;
* `Pipeline.compile() -> ExecutionPlan`;
* `RunResult` containing named outputs, warnings, per-node timings, DataFusion
  metrics, and run metadata.

Compilation validates:

* unique node IDs;
* acyclic topology;
* required and unknown ports;
* table/array kind compatibility;
* registered operators and UDFs;
* declared Arrow schemas and array constraints;
* reachable graph outputs;
* SQL input aliases and referenced ports.

Replace `Context` with a per-run `RunContext` containing:

* run and node identifiers;
* DataFusion runtime;
* engine and UDF registries;
* metrics collector;
* cancellation and deadline state;
* read-only project settings.

### Sources, batching, and checkpoints

Move batching out of `MicroBatchRunner`:

* `Source.read(cursor=None) -> Iterator[Batch]`;
* `Sink.write(batch) -> None`;
* `BatchingSource` groups records by `max_rows` and `max_bytes`;
* `MicroBatchRunner.run(source, sink=None) -> Iterator[RunResult]`;
* `StreamingRunner.step(batch) -> RunResult`.

Runners consume formed batches and never discard outputs. Synchronous iteration
provides backpressure in v0.2.

Introduce a versioned `CheckpointStore` protocol and `FileCheckpointStore`.
Checkpoints contain:

* format version;
* pipeline/config fingerprint;
* source cursor and sequence;
* JSON-compatible state keyed by node ID;
* creation timestamp.

Commit a checkpoint only after configured sinks successfully accept the output.
Delivery semantics are explicitly at-least-once.

Reject a fingerprint mismatch unless the caller resets or supplies a checkpoint
migration. Preserve atomic temporary-file replacement for filesystem
checkpoints.

### DataFusion-integrated UDF registry

Tabular UDFs are DataFusion scalar UDFs, not arbitrary table callbacks.

```python
@registry.datafusion_scalar(
    name="normalize",
    version="1",
    input_fields=[pa.float64()],
    return_field=pa.float64(),
    volatility="immutable",
)
def normalize(values: pa.Array) -> pa.Array:
    ...
```

Each registered UDF declares:

* stable name and version;
* Arrow input fields;
* Arrow return field;
* volatility: immutable, stable, or volatile;
* parameter schema;
* description;
* implementation callable.

Pipeline configurations reference UDF names and versions. They never contain
source code or Python import paths.

DataFusion registers UDFs in the run's `SessionContext`; `ExpressionOperator`
and `SqlOperator` invoke them by name. Prefer DataFusion built-ins and PyArrow
compute functions before Python UDFs.

Array UDFs use a parallel registered vectorized contract over Array API
objects.

v0.2 explicitly excludes:

* row-object UDFs;
* uploaded or inline Python;
* aggregate UDFs;
* window UDFs;
* table-generating UDFs;
* stateful UDFs.

Stateful custom behavior remains an explicit custom `Operator`.

### Project configuration and web UI

Define versioned Pydantic models:

* `ProjectConfig`;
* `PipelineConfig`;
* `NodeConfig`;
* `EdgeConfig`;
* `PortConfig`;
* `DataFusionConfig`;
* `UdfReference`;
* `DataSourceConfig`;
* `RunOptions`.

Canonical storage is formatted JSON. YAML is import/export only.

A table calculation node does not expose a backend selector. Its configuration
selects:

* expression or SQL mode;
* input port aliases;
* query/expression;
* declared output schema;
* relevant DataFusion execution options.

The local UI uses:

* FastAPI backend;
* React, TypeScript, and Vite;
* React Flow graph editor;
* generated TypeScript models from OpenAPI.

API:

* `GET /api/v1/catalog`;
* `GET/POST /api/v1/projects`;
* `GET/PUT/DELETE /api/v1/projects/{id}`;
* `POST /api/v1/projects/{id}/validate`;
* `POST /api/v1/projects/{id}/runs`;
* `GET /api/v1/runs/{id}`;
* `GET /api/v1/runs/{id}/events`;
* `DELETE /api/v1/runs/{id}`;
* project import/export endpoints.

UI capabilities:

* visual DAG editing;
* DataFusion expression and SQL editors;
* schema-aware node forms;
* registered UDF selection;
* sample CSV, JSON, Arrow IPC, and Arrow-protocol input;
* query validation and preview;
* result table display;
* DataFusion logical/physical plan inspection;
* per-node timing and row-count metrics;
* checkpoint controls;
* benchmark comparisons.

Do not expose pandas/Polars upload or engine choices. CSV and JSON inputs are
parsed directly into Arrow.

Runs execute in managed worker processes. Preview defaults are capped at 10
MiB, 100,000 rows, and 30 seconds.

The server binds only to loopback in v0.2 and has no authentication or
public-hosting mode.

## Phased Implementation

### Phase 1 — Batch model and DataFusion consolidation

* Add `Batch`, metadata, Arrow protocol adapters, and schema utilities.
* Make DataFusion and PyArrow the core tabular dependencies.
* Remove pandas/Polars engines, dependencies, exports, tests, and documentation.
* Convert the existing table expression path to DataFusion.
* Update the introduction so DataFusion is the sole table query/calculation
  engine.
* Split NumPy, JAX, web, development, and benchmark dependencies into extras.
* Publish a clean-break v0.2 migration guide.

Exit criteria:

* Arrow Table and RecordBatch inputs behave identically.
* Protocol-compatible tabular inputs normalize to Arrow.
* No pandas or Polars import exists in the package.
* All table calculations execute through DataFusion.
* Empty, chunked, nullable, dictionary-encoded, and nested Arrow inputs are
  tested.

### Phase 2 — DAG runtime and recovery

* Add ports, edges, graph compilation, linear sugar, and immutable execution
  plans.
* Add multi-input DataFusion SQL nodes for joins and aggregations.
* Return named graph outputs and execution metrics.
* Introduce source, sink, batching, cursor, and checkpoint protocols.
* Implement at-least-once recovery and fingerprint validation.
* Remove the unused runner `batch_size` parameter.

Exit criteria:

* Branching, fan-out, fan-in, multi-table SQL, cycle rejection, sink failure,
  cancellation, and checkpoint recovery pass end-to-end tests.

### Phase 3 — Registered UDFs

* Add DataFusion scalar UDF specifications and registry decorators.
* Register UDFs when creating the run-scoped `SessionContext`.
* Add array UDF registration for NumPy/JAX nodes.
* Validate parameters, Arrow types, return values, volatility, and versions.
* Add catalog discovery for Python and the UI.

Exit criteria:

* Registered scalar UDFs work in DataFusion expressions and SQL.
* Unknown versions and output-type violations fail before downstream execution.
* Python and serialized configurations produce identical results.
* No web or project configuration can submit executable code.

### Phase 4 — Configuration API and web UI

* Add versioned project models and atomic JSON persistence.
* Build FastAPI catalog, validation, run, event, cancellation, and import/export
  APIs.
* Build the React Flow editor, SQL editor, generated forms, data preview, plan
  viewer, results, and metrics.
* Add worker lifecycle and local resource limits.

Exit criteria:

* A user can build, save, reload, validate, and execute a branching DataFusion
  pipeline containing a registered UDF without writing Python in the browser.

### Phase 5 — Hardening and release

* Reconcile README, introduction, architecture, examples, and API reference.
* Document DataFusion version/configuration, SQL restrictions, UDF volatility,
  protocol ingestion, checkpoint behavior, and delivery semantics.
* Add a v0.1-to-v0.2 migration guide.
* Establish stable benchmark baselines before enabling performance gates.

## Test Framework

Continue using pytest and add:

* `pytest-cov` with a 90% core coverage floor;
* Hypothesis for generated Arrow schemas, batches, DAGs, and checkpoint state;
* `pytest-xdist` for parallel unit and contract suites;
* HTTPX for FastAPI tests;
* Vitest and React Testing Library for frontend tests;
* Playwright for browser workflows.

Test categories:

* Unit: batch normalization, metadata, schemas, expressions, graph compilation,
  and config parsing.
* DataFusion contract: projection, filtering, joins, grouping, windows, nulls,
  empty input, chunked data, nested types, SQL validation, and metrics.
* Arrow interoperability: Table, RecordBatch, Arrow C Stream, and DataFrame
  Interchange protocol stubs.
* Array contract: NumPy/JAX operations, ownership, synchronization, and explicit
  conversion.
* UDF: registration, versions, volatility, nullability, type mismatch,
  exceptions, and query integration.
* Recovery: crashes around sink/checkpoint boundaries, stale fingerprints,
  corrupt state, and cursor replay.
* Security: prohibited SQL statements, unsafe array AST nodes, unknown registry
  entries, path traversal, oversized previews, and non-loopback server binding.
* End-to-end: persisted graph execution from Python and the browser.

CI jobs:

* core unit/property tests;
* DataFusion integration tests;
* NumPy array tests;
* JAX CPU tests;
* API/frontend tests;
* browser end-to-end tests;
* scheduled benchmarks.

There is no dataframe-backend matrix because DataFusion is the only table
engine.

## Benchmark Design

Use pytest-benchmark with deterministic seeded Arrow datasets and JSON
artifacts.

DataFusion scenarios:

* projection and calculated columns;
* filters with varying selectivity;
* group-by and aggregation cardinality;
* joins with varying table size and key cardinality;
* window functions;
* built-in function versus registered Python UDF;
* SQL planning time versus execution time;
* warm `SessionContext` versus new-session startup;
* different DataFusion execution batch sizes and partition counts;
* graph fan-out and fan-in overhead;
* checkpoint serialization and recovery.

Array scenarios:

* element-wise operations;
* reductions;
* reshape and transpose;
* matrix multiplication;
* registered vectorized array UDFs;
* NumPy versus warmed JAX execution.

Dataset scales:

* 100 rows for overhead;
* 10,000 rows for small batches;
* 100,000 rows for standard CI;
* 1,000,000 rows for nightly throughput;
* larger stress cases as scheduled informational runs.

Metrics:

* planning latency;
* execution latency;
* rows per second;
* peak process RSS;
* output row count;
* Arrow buffer-copy count where observable;
* checkpoint write/load latency.

Separate cold startup, DataFusion planning, JAX compilation, and warmed
execution. Force JAX synchronization before stopping timers.

Policy:

* Run smoke benchmarks on PRs and upload results.
* Run the standard matrix nightly on stable runners.
* Initially report regressions without blocking.
* After 20 main-branch samples, gate only cases with coefficient of variation at
  or below 5%.
* Fail selected stable cases on regressions greater than 10%.
* Keep memory and stress benchmarks informational.

## Assumptions and Acceptance Criteria

* Python 3.13 remains the minimum version.
* v0.2 is a clean API break.
* DataFusion is the only table query/calculation engine.
* pandas and Polars engines, dependencies, UI options, and compatibility
  promises are removed.
* Generic Arrow protocol ingestion is supported without importing producer
  libraries.
* NumPy and JAX remain optional array engines.
* UDFs are trusted, registered, vectorized functions.
* Tabular UDFs execute as DataFusion scalar UDFs over Arrow arrays.
* Project persistence is canonical JSON with optional YAML import/export.
* The UI is local, single-user, and unauthenticated.
* Runtime delivery is at-least-once.
* Distributed execution, GPU benchmarking, public UI hosting,
  aggregate/stateful UDFs, and arbitrary code upload are out of scope.

Completion requires:

* all table calculations demonstrably execute through DataFusion;
* no pandas or Polars package dependency/import remains;
* Arrow protocol, DataFusion, DAG, checkpoint, UDF, API, frontend, and browser
  suites pass;
* a persisted branching pipeline with a multi-input DataFusion query and
  registered UDF executes identically through Python and the web UI.
