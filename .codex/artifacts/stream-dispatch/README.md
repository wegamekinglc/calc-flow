# DAL-417 第二阶段：streaming 回调判别复用

本轮消除了每批 native coroutine 在提交和分发两处的重复 Python inspect 调用，
但**两个场景均为 inconclusive，尚不能确认稳定提速、等价或排除回归**。
保留全部样本，不追加采样。主要的 Tokio ↔ asyncio 往返和 socket 通知成本仍存在；
本结果不支持把 streaming 调度优化目标宣布为已获得稳定性能收益。

## 定位与改动

基线 `main@1b8ff9cf360b5c05d62cf97e48d12d19f652c17e` 已有 eager Task 和合并唤醒。
一次实现前的小批诊断执行时钟为 24.405ms。63 个 source.next 的阶段累计为：
GIL 接入 2.363ms、准备到入队 0.757ms、入队到分发 5.664ms、分发到完成 6.734ms、
完成到 Rust 恢复 2.127ms；64 个 sink.write 相应为 2.629、0.571、9.336、4.472、1.945ms。
首个 source.next 已在启用探针前等候 gate，因此只有 63 个 source 记录。
同一诊断 cProfile 观察到约 5ms 的 epoll poll 和约 2ms 的 socket send 自耗时。
这些跨任务时钟相互重叠，cProfile/探针也有扰动，不能相加当作互斥墙钟或归因为纯 GIL。

选择边界最小的重复准备工作：每个 job 捕获 `types.CoroutineType`，原生 coroutine
按不可变的精确类型识别一次，将布尔结果放入本次请求，由分发器复用。
每次分发仍读取当前 task factory；Future、generator-based coroutine 和 custom awaitable
继续由原 inspect/asyncio 路径处理。新增类型引用参加现有 GC traverse，无全局执行缓存。
三个输入批次的定向反例在旧 native 上观察到 **14 次**相关 inspect 调用，候选为 **0 次**。
此项证明重复工作消除，并不量化其在整体时间中的独占份额。

产品提交 `cfa2a2a2f2d5a84cc5171c11261a3c8f1ce7dece` 只改绑定层判别、相应测试构造
及一段文档。批形状、输出顺序、队列容量、源轮询、背压、控制消息和取消所有权保持原路径。
没有修改 Arrow 转换实现；与 DAL-475 / PR #515 保持分支和责任边界。

## 测量边界与阶段

复用既有 Arrow fixture 和严格列/值/顺序 oracle，仅执行整表和固定 64×512。
每场景两轮十对相邻 AB/BA，**80 次正式观测、1,310,720 行输出**，另四次预检。
原始 IPC 小批输出仍为 64×256，没有合批。四个实现前诊断进程都使用基线 wheel，
包括目录名标作 head 的两个重复基线；其 seals 单独保留，不混入候选统计。

新进程先暖身首批，再从已备输入 gate 计时到父进程 Arrow read_all；正常输入校验、
Batch/Arrow 转换、回调执行、逐批消费、concat 和输出 IPC 都在正式时钟内。
源在输出完成前不发 EOF，随后取消并等待清理。准备与暖身单列，不隐藏冷启动成本。
