# DAL-417：CF SQL 与真实 Arroyo 的直接 Arrow 对照

**本轮中位数结论：Arroyo 比 CF SQL 普通 collect 和预编译图执行都快，小批差距更大。**
以双方“已备输入放行，到父进程完整消费输出 Arrow Table”为相同计时边界：
整表的成对吞吐比分别为 **2.09×、1.42×**；64×512 小批分别为 **18.13×、13.32×**。
这个指标含输出 IPC、门控和观察成本。整表预编译范围跨过 1×，其中一次 CF 更快，
不能把中位数解读为每次胜出。没有因为接口不同而放弃测试，也没有用替代算法。

## 同口径绝对吞吐和范围

全部使用同一 32,768 行过滤/投影输入；单位为 **万输入行/秒**，五次中位数（min–max）。
“预编译”指提前建立 CF native graph，不是缓存每次 DataFusion 物理执行计划。

| 输入形状 | CF SQL 普通 collect  | CF SQL 预编译图      | 真实 Arroyo            |
|----------|----------------------|----------------------|------------------------|
| 整表一次 | 458.6（416.8–470.1） | 697.4（342.0–703.2） | 931.4（553.8–1,412.8） |
| 64×512   | 50.18（49.48–51.42） | 66.02（59.40–71.04） | 905.8（710.7–1,108.4） |

每组 Arroyo 位于两个 CF 路径之间；方向为 **Arroyo/CF**，取五个相邻比值的中位数，
不是将上表两列中位数直接相除：

| 输入形状 | 相对普通 collect         | 相对预编译图             |
|----------|--------------------------|--------------------------|
| 整表一次 | 2.090×（1.178–3.390）    | 1.421×（0.794–3.784）    |
| 64×512   | 18.133×（13.821–22.090） | 13.322×（10.005–17.726） |

对应整次完整结果延迟（ms，中位数及范围），并非每行延迟：

| 输入形状 | CF collect              | CF 预编译图             | Arroyo               |
|----------|-------------------------|-------------------------|----------------------|
| 整表一次 | 7.145（6.970–7.862）    | 4.698（4.660–9.582）    | 3.518（2.319–5.917） |
| 64×512   | 65.307（63.724–66.221） | 49.635（46.128–55.169） | 3.618（2.956–4.611） |

这些是同机短 burst 五组的描述性结果，不是长期流式稳态、裸算子 CPU 排名或仓库回归门禁。
整表预编译有一次输出 IPC 约 5.965ms，Arroyo 整表也有 1.576ms 的输出 IPC；完整结果消费
范围如实保留，不按异常值删样。新旧阶段不混样，不用旧 streaming 样本补新配对。

## 不含输出 IPC 的 API / 引擎结果阶段

为回答计算及正常调用本身花多少时间，另列引擎内结果已就绪的观测。
CF 从开始逐次调用到全部 Arrow Table 和最终 concat 可用，**保留正常输入绑定、规划、
调用和结果包装**。Arroyo 使用已验证 binary 的 native core 加公开输出列 projection 两个
顺序阶段之和：完整原生 Arrow batches 已在 sink 持有，不含输出 IPC；不是额外连续时钟，
两个计时点间的观察器记账微小间隙未测。两者接口/准备位置不同，不称完全相同的裸内核。

五次中位数（范围），吞吐仍为万输入行/秒：

| 输入形状 | CF collect           | CF 预编译图                | Arroyo Arrow 结果阶段      |
|----------|----------------------|----------------------------|----------------------------|
| 整表一次 | 593.7（539.3–631.0） | 1,279.2（1,049.9–1,307.1） | 2,500.5（2,162.5–2,682.8） |
| 64×512   | 52.14（51.12–52.98） | 69.40（63.22–74.51）       | 2,548.6（2,408.0–2,920.8） |

该结果阶段的成对比值也直接来自本轮同组新观测：

| 输入形状 | Arroyo/collect           | Arroyo/预编译图          |
|----------|--------------------------|--------------------------|
| 整表一次 | 4.211×（3.537–4.811）    | 2.097×（1.654–2.382）    |
| 64×512   | 49.113×（46.185–55.125） | 39.200×（34.698–42.206） |

这两个表解释正常 SQL API/重复有限调用与持有已建物理图的持续执行之间的应用成本差异。
Arroyo 的 SQL/物理图编译在 job ready 前；CF collect 每次按 API 合同准备/编译 native graph，
预编译路径只提前建立 graph，执行期的 DataFusion 工作仍在。不是通过隐去 CF 正常成本
制造优势，也不是证明全部差距都来自规划或 Python；计时器/控制文件成本未做独占剖析。

## 时间到底包含什么

| 阶段             | CF collect                                                            | CF 预编译图                                                | Arroyo                                                                  |
|------------------|-----------------------------------------------------------------------|------------------------------------------------------------|-------------------------------------------------------------------------|
| ready 前准备     | Runtime/声明、解码 IPC、caller Table views                            | 同前，另 lowering/compile native graph                     | CLI/embedded 服务、SQL/物理图编译、IPC 解码、schema cast/内部 timestamp |
| 放行后的正常工作 | 每批 collect_async，含正常 binding、prepare/compile、执行及 `_tables` | 每批 Batch.from_pyarrow、execute_async、outputs/to_pyarrow | SourceCollector → 真实 SQL physical graph → 完整 native batch sink      |
| 结果包装         | `_tables` 与最终 concat 在 API 内                                     | outputs/to_pyarrow 与 concat 在 API 内                     | 去内部 `_timestamp` 的 projection，core 后、IPC 前                      |
| 共同完整消费区间 | start gate → encode/EOS/close/rename → parent read_all                | 同前                                                       | 同前                                                                    |
| 区间之外         | 生成输入、全量正确性校验、图/metrics JSON、退出                       | 同前                                                       | 同前，消费后才放行 source Final/EOF 并显式停止 CLI                      |

CF 对 `_collect_batches`、`_prepare_collect_batches`、`_tables` 仅加包裹原函数的嵌套时钟，
不提前调用、不改返回、不去掉正常成本。hooks 在 ready 前安装，所有 span 都在 API 总时钟内；
每次有 1 或 64 个调用记录。计时 hook 及 Python bookkeeping 是外部测试适配开销，未测出
可独占份额，也未从总时间扣减。预编译输入/执行/包装直接分段。图/最后一次 DF metrics
读取在结果 IPC 发布后，避免放进执行→发布的关键路径。JSON 从未承载行数据。

各阶段中位数（ms；全部五次范围在 `data/summary.json`），内含项不能再次加总或扣成独占 CPU：

| 整表 / Arroyo    | 1.310          | 提前 0.129         | ready 前，未拆分     | 0.003    | 不适用      | 0.231    |
| 64×512 / collect | 62.849         | 2.376              | 8.949                | 1.751    | 0.065       | 0.595    |
