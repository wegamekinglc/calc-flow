## Blocking findings

### B1 — Python `str` was broader than the Rust strict-JSON transport

**Status: Resolved in the design artifacts.**

#### Evidence

- The pre-review API note accepted every exact Python `str` as a settings key
  or scalar and encoded it with `json.dumps`.
- Python strings can contain code points in `U+D800..U+DFFF`.
- The locked dependency is `serde_json 1.0.150`
  (`Cargo.lock`), and the native transport terminates in
  `serde_json::Value::String` / Rust `String`.
- `serde_json` rejects an escaped lone surrogate on the string path. An
  escaped leading/trailing pair is decoded as one Unicode scalar, so a Python
  string containing two surrogate code points would not round-trip as the
  same value.
- The core strict parser is built around `String` keys and
  `Value::String` (`crates/calc-flow/src/json.rs:132-140,169-183`).

#### Impact

The public constructor could accept a value that:

- fails only at native execution with the generic private transport error; or
- changes value while crossing Python → JSON → Rust.

That violates constructor-time validation, immutable value semantics, exact
provider observation, and the claim that valid public options always fit the
private transport.

#### Minimal amendment

Both design artifacts now:

- accept ordinary Unicode scalar text;
- reject every surrogate code point, paired or unpaired, in keys and values;
- use the exact redacted public error
  `settings at <path> contains a non-portable Unicode string`;
- require tests for lone leading, lone trailing, and paired Python surrogate
  code points in keys and values;
- require the native direct-call parser to reject malformed surrogate JSON
  without exposing parser details.

This is narrower than "all Python `str`" but is the only lossless contract
compatible with Rust `String`. No valid Unicode scalar text is removed.

### B2 — Error precedence conflicted with the existing engine order

**Status: Resolved in the design artifacts.**

#### Evidence

- The pre-review specification said that when a callback throws first, the
  existing provider error mapping should be retained.
- The API note instead said `CancelledError` wins if the deadline is expired
  at the post-operator check.
- The baseline core is unambiguous:
  `process()` returns into `process_result`, then
  `node_context.check_cancelled()?` runs, and only then is
  `process_result?` unwrapped
  (`crates/calc-flow/src/pipeline.rs:639-646`).
- Before the first execution check, the core acquires the run lock, recovers a
  prior marker, validates inputs, snapshots state, and records rollback
  (`crates/calc-flow/src/pipeline.rs:288-307,405-419,529-546`).
- Existing Rust tests already pin cancellation-over-operator-error
  (`crates/calc-flow/tests/pipeline_execute.rs:735-750`).

#### Impact

An implementer could add a Python provider test expecting the wrong exception
or accidentally reorder the core checks. The original wording also left
expired-deadline precedence versus recovery/input/snapshot errors unclear.
That would make rollback and cross-language error behavior non-deterministic.

#### Minimal amendment

The specification and API note now freeze the actual lifecycle:

1. malformed private transport fails before the plan lock and state lifecycle;
2. after the lock, recovery, input validation, snapshot, and marker creation
   retain precedence over the first deadline check;
3. an expired deadline is detected before the first operator call;
4. after an operator returns, cancellation/deadline is checked before its
   result is unwrapped, so `CancelledError` wins over a simultaneous provider
   error;
5. cancellation while merely waiting for the lock creates no marker;
6. cancellation after marker creation uses the existing one-marker recovery
   path and must not add a watcher or second rollback/completion path.

The test contract now requires each relevant precedence, including a real
provider path.

### B3 — The abbreviated worker rule was not mode-closed

**Status: Resolved in the specification.**

#### Evidence

- Public and mapped providers are distinct baseline registration modes:
  `Runtime.register_provider()` records a single-array provider, while
  `_register_mapping_provider()` records `provider_mode="mapping"` and exact
  ports (`python/calc_flow/pipeline.py:101-170`).
- Worker restoration branches on that mode
  (`web-ui/backend/src/calc_flow_studio/run_manager.py:622-649`).
- 5.1 freezes mapped NumPy/JAX `table_matmul@1` as a separate two-argument
  registration contract and keeps capability v1 closed.
- The API note correctly required mapped `True` or any non-bool value to fail
  closed, but the specification's short table said `True → three arguments`
  without scoping that row to public single-array registrations.

#### Impact

Following the abbreviated rule literally would extend the private mapped
provider callback surface, contradict the 5.2 non-goal, and let a malformed
worker projection bypass the intended fail-closed boundary.

#### Minimal amendment

The specification now contains the same mode-sensitive closed table as the
API note:

- public single-array missing/false → two arguments;
- public single-array true → three arguments;
- mapped missing/false → existing mapped two-argument callback;
- mapped true or any other value → fixed redacted reconstruction failure.

The worker must derive this flag only from the selected trusted parent
registration snapshot. It must never accept the flag from project JSON, REST,
capability JSON, source, import path, or an arbitrary installed package.

## Non-blocking findings and residual risks

### N1 — No settings byte/item limit is acceptable here, but amplification is real

The approved contract has a depth limit but no byte-count or item-count limit.
That is acceptable for 5.2 because:

- this is a local, trusted Python call surface;
- project/REST/Studio input cannot source settings;
- the worker still calls `plan.execute(batches)` with empty options;
- callers can already supply much larger execution batches.

The provider bridge will nevertheless serialize/copy the settings snapshot for
each opted-in operator invocation. A large snapshot can therefore amplify CPU
and memory by the number of callbacks. The API note now records the deliberate
absence of a cap. Implementers should avoid any additional log/repr copy. A
future cap must be a documented public compatibility decision with a stable
error, not a hidden native threshold.

### N2 — The GC contract needs two traversed roots, not merely two Rust handles

The current native runtime stores and traverses `PythonRoot` values
(`crates/calc-flow-python/src/config.rs:15-41,117-146,404-412`), and a compiled
plan retains the runtime wrapper as its owner
(`crates/calc-flow-python/src/config.rs:382-397`).

For an opted-in provider, both the application callback and the package-private
execution-options factory must be retained through that same traversed
ownership graph. Merely storing `Py<PyAny>` inside an opaque factory without
visiting it is insufficient. Duplicate-registration failure must release both
new roots. The required cycle/release tests make this an implementation risk,
not a remaining contract blocker.

### N3 — Native parsing must remain private or be duplicated in the binding

The core duplicate-aware parser is `pub(crate)` inside the Rust engine
(`crates/calc-flow/src/json.rs:49-59,90-183`), while the PyO3 binding is a
separate crate. 5.2 approves no new Rust public parser. Therefore the binding
must either implement its own private duplicate/depth/object checks or use an
existing non-public crate-internal arrangement without exporting a new Rust
API. Broadening the Rust public surface beyond `RunContext::deadline()` would
violate the freeze.

### N4 — Python immutability is frozen-value semantics, not a hostile-runtime sandbox

A frozen, slotted pure-Python object gives the requested normal assignment and
deletion failures, defensive snapshots, stable equality/hash, no instance
`__dict__`, and redacted repr. As with any pure-Python frozen dataclass,
deliberate use of low-level mutation primitives is outside the API contract.
This does not weaken the worker boundary because project/REST data cannot
construct the object or its private transport.

### N5 — Custom mapping and timezone methods can execute caller code during construction

Supporting `Mapping` and aware `datetime` necessarily calls caller-provided
mapping/tzinfo methods while taking the snapshot. The contract correctly:

- retains none of those objects;
- wraps failures with `raise ... from None`;
- excludes raw repr, key, value, timezone name, offset, and timestamp.

This is acceptable for a trusted local caller. No such method may run later in
the native operator path because only canonical text and an exact base UTC
`datetime` are retained.

## Axis review

### `ExecutionOptions` value contract

**Pass after B1.**

- Canonical JSON text plus an exact base UTC `datetime` is sufficient for
  equality and hash.
- Frozen slots plus canonical internal text and decode-on-read prevent shallow
  mutability leaks.
- Exact repr/str forms contain only empty/redacted and unset/set markers.
- Portable integer limits match serde JSON's signed/unsigned domains.
- Finite float, depth 32, path-local cycle detection, duplicate custom-mapping
  keys, and alias copying are implementable.
- Surrogate rejection closes the only lossy Python/Rust text case found.
- Fixed six-digit UTC text avoids platform timestamp APIs and float precision
  loss.

### Sync/async execution and lifecycle

**Pass after B2.**

- The wrapper can preserve the current regular-method `execute_async()` shape,
  call-time input copy, and event-loop precedence
  (`python/calc_flow/pipeline.py:274-298`).
- Native settings/deadline parsing can happen before
  `ExecutionPlan::execute()` acquires the run lock.
- The absolute deadline is naturally not extended by lock wait because the
  captured instant enters `RunContext` unchanged.
- Existing pre/post-node checks provide cooperative cancellation and zero
  operator calls for an already-expired deadline.
- Existing transaction markers and next-operation recovery are the only safe
  cancellation path; no background deadline task is needed.
- The expanded tests cover lock wait, cancellation races, rollback, reuse, and
  error precedence rather than only value construction.

### Provider callback compatibility and real operator path

**Pass.**

- A default-false keyword-only registration flag is additive.
- Exact bool validation before the registration lock preserves successful-only
  revision behavior.
- Factory presence fixes arity without introspection, trial calls, or
  `TypeError` retry.
- `.validate(operator_options)` remains compile-time and two-argument provider
  callbacks remain unchanged.
- The third argument is rebuilt from the actual
  `OperatorContext.run`; it is not a default object or caller alias.
- Mapped helpers and NumPy/JAX registrations remain two-argument.
- The acceptance matrix explicitly requires compiled real-provider execution,
  callback call counts, state mutation, and cross-node isolation.

### Rust accessor and PyO3 bridge

**Pass.**

`RunContext::deadline() -> Option<&DateTime<Utc>>` borrows from `&self`; its
lifetime is unambiguous and matches `settings()`. `OperatorContext` already
exposes `pub run: &RunContext`, so another accessor would be redundant. A
`const fn` using `Option::as_ref()` is valid on the pinned Rust 1.88 toolchain.
The provider formats the borrowed value while the operator context is alive
and does not retain the reference across Python ownership boundaries.

### Worker and 5.1 boundary

**Pass after B3.**

- Selection remains exact-reference filtering
  (`run_manager.py:581-619`).
- Only selected trusted registration records are serialized
  (`run_manager.py:664-682`).
- The bool does not change cloudpickle availability or any capability
  reconstruction discriminator.
- Capability assembly already consumes a data-only whitelist under one
  registration lock; it must ignore the new private key.
- Studio still invokes the public plan without options
  (`run_manager.py:685-704`).
- Capability schema v1, catalog, validation/run/result unions, decoders,
  OpenAPI, generated TypeScript, project v2, checkpoint, and lazy DataFusion
  remain unchanged.

## Required implementation guardrails

1. Do not broaden the approved public surface beyond:
   `ExecutionOptions`, two keyword-only `options` parameters,
   `accepts_execution_options`, and borrowed Rust `deadline()`.
2. Reject surrogate code points during Python construction, before canonical
   JSON is stored; do not defer a valid-looking public value to native failure.
3. Parse both private transports before acquiring the plan lock. All parser
   errors must discard source details and exception chaining.
4. Preserve the exact existing lifecycle and error order. Do not add a
   deadline watcher, second Tokio task, reused token, or second rollback path.
5. Call a provider exactly once. Never inspect its signature or retry after
   `TypeError`.
6. Build the third argument from `OperatorContext.run.settings()` and
   `RunContext::deadline()`, with a fresh exact Python value per invocation.
7. Retain and GC-traverse callback and private factory roots through Runtime,
   compiled plan, active async task, cancellation, and recovery.
8. Keep mapped providers and NumPy/JAX helpers on the existing two-argument
   path; reject mapped true/non-bool worker projections before registration.
9. Keep `accepts_execution_options` out of provider identity, fingerprint,
   project/checkpoint data, capability v1, REST, OpenAPI, and generated
   TypeScript.
10. Do not refactor existing project/checkpoint strict-JSON errors unless their
    exact compatibility behavior remains separately pinned.
11. Do not log, repr, or wrap settings/deadline/native parser text. Existing
    application callback error text remains governed by the existing
    non-Studio provider contract.
12. Prove the declared non-change files against baseline, not merely by
    observing that a generator command succeeded.

## Recommended implementation sequence

1. **Pure Python value and RED tests**
   - private label-aware canonicalizer;
   - surrogate/depth/range/cycle/copy/redaction tests;
   - UTC normalization, equality/hash/repr/slots/export tests.
2. **Rust accessor and native execution transport**
   - borrowed deadline accessor;
   - duplicate-aware strict object parser and exact deadline parser;
   - fresh cancellation token in sync and async paths;
   - before-lock failure and deadline-order tests.
3. **Public provider opt-in and bridge**
   - strict registration flag;
   - callback/factory GC roots;
   - actual `OperatorContext.run` reconstruction;
   - legacy/opted arity and no-retry tests.
4. **Worker projection and 5.1 regressions**
   - closed mode/flag validation;
   - missing/false/true public records;
   - missing/false/true/other mapped records;
   - capability/revision/transportability invariants.
5. **Concurrency, cancellation, rollback, and ownership**
   - same-plan lock wait;
   - queued cancellation;
   - expired-before-first-node;
   - mid-node/post-node precedence;
   - marker recovery exactly once;
   - subsequent reuse and cycle collection.
6. **Docs and no-drift gates**
   - public references/example;
   - absolute/cooperative deadline;
   - local settings versus Studio limits;
   - project/OpenAPI/generated/capability golden no-change.
7. **Independent tester → reviewer → doc writer**
   - tester owns the reproducible matrix;
   - reviewer owns the final implementation and GitHub-thread gate;
   - doc writer reconciles release notes after review.
