## 2. 现状与必须解决的缺口

Rust core 已有：

```rust
pub struct ExecutionOptions {
    pub settings: JsonMap,
    pub deadline: Option<DateTime<Utc>>,
    pub cancellation: CancellationToken,
}
```

执行时它被转换为 `RunContext`。`RunContext` 已公开只读 `settings()`，在每个
operator 前后执行 deadline/cancellation 检查，但没有公开 deadline accessor。

Python/PyO3 的同步和异步执行入口目前都固定传入
`ExecutionOptions::default()`。Python 自定义 provider callback 的既有签名为：

```python
callback(batch, operator_options)
```

原生 Python provider bridge 当前丢弃 `OperatorContext`。因此只给
`ExecutionPlan.execute()` 增加 `options=` 参数并不足以满足验收条件：执行设置可以
进入 Rust `RunContext`，但自定义 Python provider 仍观察不到它们。

设计必须同时解决：

1. 每次执行的 Python 值对象和 native 传输；
2. 自定义 provider 对 settings/deadline 的显式、向后兼容访问；
3. 现有两参数 callback、取消、回滚、5.1 capability/worker 契约不回归。

## 3. 目标

### 3.1 功能目标

- 新增不可变、纯数据的 Python `ExecutionOptions`：
  - `settings` 是严格 JSON object；
  - `deadline` 是 timezone-aware `datetime` 表示的绝对时刻；
  - 构造时完成验证、深拷贝和 UTC 归一化。
- `ExecutionPlan.execute()` 与 `execute_async()` 新增 keyword-only
  `options`。
- 同一次执行中的同步或异步 Python provider 能显式选择接收相同的 settings 和
  UTC deadline。
- 每次调用都使用独立的执行 options 和独立的内部取消 token。
- deadline、异常和 asyncio 取消都沿用现有事务回滚保证。

### 3.2 兼容目标

- 所有未传 `options` 的调用保持现有行为。
- 现有两参数 provider callback 不改变调用参数数量。
- 已保存 project v2、checkpoint、Studio REST/OpenAPI、generated TypeScript 和
  5.1 capability v1 均不改变。
- 新能力是 keyword-only、显式 opt-in；不存在 callback 签名猜测。

### 3.3 安全目标

- settings 只能包含严格 JSON 数据，不能携带 callable、模块、类实例、路径语义或
  导入描述。
- settings/deadline 不进入异常文本、`repr` 或默认日志。
- worker 仍只重建 parent 已选择且允许传输的 registration；5.2 不把任意项目输入
  变为可执行内容。

## 4. 非目标

- 不新增或修改 Rust `ExecutionOptions` struct 的公共字段。
- 不向 Python 暴露 `CancellationToken`，不新增手动 cancel API。
- 不让 Python source、sink、scalar UDF 或私有 mapped provider 获得执行上下文。
- 不让 deadline 抢占正在运行的同步 Python callback；它只在既有安全边界协作检查。
- 不把 Studio preview 的行数、字节数、墙钟时间或资源限额放入
  `ExecutionOptions.settings`。
- 不修改 project v2 schema、checkpoint 编码、lazy DataFusion 计划或结果 union。
- 不修改 `/api/v2/catalog`、`/api/v2/capabilities`、validation/run/result REST
  模型。
- 不新增 capability v1 字段，也不伪造 capability v2。
- 不把 provider transportability 解释为“任意项目输入均可执行”。

## 5. 备选方案

### 方案 A：只给 execute 增加 options

PyO3 接收 settings/deadline 并构造 Rust `ExecutionOptions`，provider callback
保持不变。

优点：变更最小。

缺点：Python provider 无法观察 settings/deadline，直接违反 5.2 的核心验收条件。

结论：拒绝。

### 方案 B：所有 provider callback 无条件增加第三个参数

所有 callback 改为：

```python
callback(batch, operator_options, execution_options)
```

优点：调用模型简单。

缺点：这是现有 Python provider 的破坏性 source break；用
`inspect.signature()` 或捕获 `TypeError` 自动猜测签名又会在装饰器、可变参数、
builtin callable 和 callback 内部 `TypeError` 上产生歧义。

结论：拒绝。

### 方案 C：显式注册 opt-in（建议）

保持现有 callback 默认两参数；注册 provider 时由调用方显式声明接受执行 options：

```python
runtime.register_provider(
    provider,
    name,
    version,
    callback,
    *,
    options_schema=None,
    accepts_execution_options=True,
)
```

默认 `False` 时：

```python
callback(batch, operator_options)
```

为 `True` 时：

```python
callback(batch, operator_options, execution_options)
```

优点：

- 对现有 provider 完全向后兼容；
- 不依赖运行时签名猜测；
- callback 内部抛出的 `TypeError` 不会被误判为签名协商；
- worker 能通过一个闭合的布尔 registration 字段重建相同调用约定；
- 不需要改变 5.1 capability schema。

代价：公共 `Runtime.register_provider` 多一个 keyword-only 参数，必须同步 stub、
文档和 worker 私有 registration 投影。

结论：方案 C 已由 API designer 批准；精确参数名、签名和错误契约见冻结 API note。

## 6. 已冻结公共契约

### 6.1 Python `ExecutionOptions`

新增专门模块 `python/calc_flow/execution.py`，并从 `calc_flow` 顶层导出：

```python
@final
class ExecutionOptions:
    def __init__(
        self,
        *,
        settings: Mapping[str, JSONValue] | None = None,
        deadline: datetime | None = None,
    ) -> None: ...

    @property
    def settings(self) -> dict[str, JSONValue]: ...

    @property
    def deadline(self) -> datetime | None: ...
```

契约：

- `settings=None` 等价于空 object。
- 根值必须是 mapping；所有 key 必须是精确 `str`。
- 允许的叶值仅为 `None`、精确 `bool`、可移植范围内的精确 `int`、有限精确
  `float` 和精确 `str`。
- key 与字符串叶值均不得包含 `U+D800..U+DFFF` surrogate code point；Python
  允许此类字符串，但 Rust `String` 无法无损表示，lone surrogate 会被
  `serde_json` 拒绝，成对 surrogate 会被规范化为单个 Unicode scalar。
- 容器仅接受支持契约的 mapping/list 形态；最大深度沿用项目严格 JSON 边界 32；
  循环引用拒绝。
- 构造时完成规范化深拷贝；以后修改原 mapping 或嵌套容器不得影响对象。
- `settings` 属性返回不能改变对象内部状态的新副本。内部保存规范 JSON，
  每次读取返回新 JSON tree；不可只依赖 frozen dataclass 的浅冻结。
- `deadline` 必须是 timezone-aware `datetime`，`utcoffset()` 不得为 `None`。
- deadline 归一化为 `timezone.utc`，保存同一绝对时刻，精度固定为 Python
  `datetime` 的微秒精度；native 传输不得经过浮点 epoch。
- `repr`/`str` 不包含 settings 内容；最多显示 settings 已设置与 deadline 是否存在，
  防止凭据进入日志。
- 对象不含 cancellation token、callback、路径、模块或其他可执行对象。

“不可变”指对象的执行语义在构造后固定。调用方可以修改从 `settings` 读取到的副本，
但不能改变内部快照。

### 6.2 `ExecutionPlan`

冻结签名：

```python
from collections.abc import Awaitable


def execute(
    self,
    inputs: Mapping[str, Batch],
    *,
    options: ExecutionOptions | None = None,
) -> RunResult: ...

def execute_async(
    self,
    inputs: Mapping[str, Batch],
    *,
    options: ExecutionOptions | None = None,
) -> Awaitable[RunResult]: ...
```

契约：

- `options=None` 与新建空 `ExecutionOptions()` 等价。
- `options` 不是 `ExecutionOptions | None` 时，进入 native 前抛 `TypeError`。
- 同步、异步使用同一规范化 settings/deadline。
- 每次调用都创建新的内部 native cancellation token；Python 对象不持有或复用它。
- inputs 仍沿用当前 wrapper 的防御性 mapping 拷贝行为。

### 6.3 provider opt-in

`Runtime.register_provider()` 新增 keyword-only：

```python
accepts_execution_options: bool = False
```

契约：

- 必须是精确 `bool`；不接受整数 `0/1` 或 truthy 对象。
- `False` 时 callback 调用形态保持两个位置参数。
- `True` 时每次调用增加第三个位置参数 `ExecutionOptions`。
- 第三个参数是从该 operator 实际 `RunContext` 重建的只读快照，不是最初调用方对象
  的可变别名。
- 同一 execution 内各 opt-in provider 看到相等的 settings 和 UTC deadline。
- callback 修改其 `settings` 返回副本不得影响后续 operator 或调用方。
- callback 返回值和异常映射保持现有 provider 契约；参数数量错误等 callback 失败
  继续映射为现有 provider error。
- opt-in 只适用于公共单-batch `register_provider`。私有 mapped provider、NumPy/JAX
  built-in 的既有两参数调用不在 5.2 扩展范围。
- flag 验证失败或后续 registration 失败均不算成功注册，不推进 5.1 runtime
  capability revision。

不使用 callback 签名探测、`contextvars` 隐式全局状态或“先调用三参数、捕获
`TypeError` 后重试”的协商方式。

### 6.4 Rust/PyO3 bridge

Python provider bridge 需要从 operator 的实际 `RunContext` 取得 deadline。给
Rust core 增加只读 additive API：

```rust
impl RunContext {
    pub const fn deadline(&self) -> Option<&DateTime<Utc>>;
}
```

这是唯一批准的 Rust 公共面变更；现有 `ExecutionOptions` struct 不变。

PyO3 内部执行入口可接收规范化后的 settings/deadline 私有表示，再构造：

```rust
ExecutionOptions {
    settings,
    deadline,
    cancellation: CancellationToken::new(),
}
```

约束：

- settings 的 native 转换必须再次保持 strict JSON，不接受 Python object fallback。
- deadline 的 private transport 保留微秒并表示绝对 UTC 时刻，不能用浮点秒。
- provider bridge 只在 registration flag 为 `True` 时构造第三个 Python 参数。
- 从 Rust `RunContext` 重建 Python `ExecutionOptions` 时不得经由公开构造器做有副作用
  的导入或执行；可使用受控的包内工厂。
- `_native` 的额外参数属于 binding 实现细节，但 `_native.pyi` 必须精确反映它。

实现形态固定为“纯 Python 冻结值对象 + package-private factory + 私有 native
传输”。settings 使用 canonical JSON 文本，deadline 使用
`YYYY-MM-DDTHH:MM:SS.ffffffZ`；不使用 native pyclass 或浮点 epoch。

## 7. 数据流与状态机

### 7.1 数据流

```text
caller mapping/datetime
        │
        ▼
Python ExecutionOptions
  strict JSON validation
  defensive snapshot
  aware datetime → UTC
        │ private data-only transport
        ▼
PyO3 ExecutionPlan.execute(_async)
  fresh CancellationToken
        │
        ▼
Rust ExecutionOptions → RunContext
        │
        ├── existing deadline/cancellation checks
        │
        └── OperatorContext
              │
              ├── legacy provider: (batch, operator_options)
              └── opted-in provider:
                  (batch, operator_options, ExecutionOptions snapshot)
```

worker 只在恢复已选择 registration 时传递
`accepts_execution_options`。运行项目本身仍不能提供 callback、source、module path
或其他执行载荷。

### 7.2 单次执行状态机

```text
PREPARED
  │
  ▼
WAIT_PLAN_LOCK
  │
  ▼
VALIDATE_INPUTS_AND_SNAPSHOT
  │
  ▼
BEGIN_ROLLBACK_SCOPE
  │
  ▼
CHECK_CANCEL_OR_ABSOLUTE_DEADLINE
  ├── cancelled/expired ───────────────┐
  ▼                                   │
RUN_NODE → CHECK → RUN_NODE → CHECK   │
  ├── error/cancel/deadline ──────────┤
  ▼                                   ▼
COMMIT                            ROLLBACK
  │                                   │
  ▼                                   ▼
COMPLETED                         FAILED/CANCELLED
```

绝对 deadline 从调用方给出的时刻开始有效，不因等待 plan lock 而顺延。它可能在锁等待、
输入检查或 snapshot 期间到期；进入第一个 operator 前必须检查，已过期时不能调用
operator。现有事务 snapshot/rollback 仍负责恢复 state。

### 7.3 并发隔离

- 每个调用捕获独立的 settings/deadline 快照。
- 同一 plan 的并发调用继续由现有 plan transaction lock 串行化。
- 一个调用等待锁时另一个调用不得覆盖其 options。
- 一个 callback 修改读取到的 settings 副本不得影响同一执行的后续 callback。
- 异步任务取消后，其 token、task 和 options 不得被下一次执行复用。

## 8. deadline 与取消语义

- deadline 是绝对 UTC 时刻，不是 timeout duration。
- 在第一次 operator 调用前已经到期时，返回现有 Python `CancelledError`，operator
  调用计数保持 0。
- 在节点之间到期时，于下一既有检查点取消并回滚。
- 同步 Python callback 正在执行时不做强制线程中断；deadline 只能在 callback 返回后
  的安全检查点生效。文档必须明确这是 cooperative deadline。
- `execute_async()` 的 task cancellation 保留现有 Python→native cancellation 映射。
- deadline 与显式 asyncio cancellation 都不得产生双重 completion、重复回滚、遗留
  token 或后台 task。
- 既有生命周期顺序保持不变：private transport 在 plan lock 前失败；拿锁后的
  recovery、输入验证、state snapshot 与 rollback marker 失败均早于第一次 deadline
  检查并保留既有优先级。
- 若 callback/operator 返回错误，而同一 post-operator 检查发现 deadline 到期或
  cancellation，则既有 `check_cancelled()` 顺序优先，返回 `CancelledError`，之后才会
  解包 operator 结果；5.2 不得把它改成 provider error。
- async task 仅在等待 plan lock 时取消不会创建 transaction marker；marker 创建后取消
  继续只由既有单一 recovery 路径恢复，不新增 watcher、第二次 rollback 或第二次完成。

## 9. 错误契约与脱敏

| 输入/阶段                                      | 错误类别              | 约束                                            |
| ---------------------------------------------- | --------------------- | ----------------------------------------------- |
| `settings` 非 mapping                          | `TypeError`           | 指明 `settings` 需要 mapping，不打印值          |
| key 非字符串                                   | `ValueError`          | 指明 strict-JSON object key 约束，不打印 key 值 |
| key/string 含 surrogate code point             | `ValueError`          | 指明非 portable Unicode，不打印 key/value       |
| 非 JSON 值、非有限 float、越界 int、循环、过深 | `ValueError`          | 带结构位置，不包含原始值                        |
| `deadline` 非 datetime                         | `TypeError`           | 不打印对象 repr                                 |
| naive datetime、无效 offset、归一化越界        | `ValueError`          | 指明需 timezone-aware、可表示的 UTC 时刻        |
| `options` 类型错误                             | `TypeError`           | 在 native 执行和状态变更前失败                  |
| opt-in flag 非精确 bool                        | `TypeError`           | 注册失败，revision 不推进                       |
| deadline 已到/执行中到期                       | 现有 `CancelledError` | 事务回滚，不新增异常类型                        |
| opted-in callback 调用失败                     | 现有 provider error   | 不把 raw callback/input/settings 放入新包装文本 |
| native/private transport 结构违约              | 内部错误              | 对外只给闭合、脱敏信息                          |

错误测试应断言稳定类别、结构位置与敏感值不出现，而不是绑定整段内部实现文本。现有
strict-JSON helper 的错误文案使用 `project` 标签；实现应抽出 label-aware 的共享纯函数，
不能把该错误前缀原样泄漏到 `settings` API。

## 10. 与 5.1 capability/worker 契约的接口

### 10.1 保持不变

- `CapabilitySnapshot.schema_version` 继续严格为 1。
- provider/operator/port/option metadata 的闭合集合不增加
  `accepts_execution_options`。
- runtime session UUID 与成功 registration 才推进 revision 的语义不变。
- snapshot 继续在单一锁内构造并与后续 revision 隔离。
- `/api/v2/catalog` 继续保持 UDF-only 旧契约。
- `/api/v2/capabilities`、Validation、Run、table/array result 的 closed unions 不变。
- frontend v1 raw decoder 的 strict extra-field 拒绝不变。
- NumPy/JAX `expression@1` 与 mapped `table_matmul@1` capability metadata 不变。

### 10.2 worker 私有投影

parent 侧 registration 快照只为公开 single-array provider registration 增加一个
内部布尔值。worker reconstruction 按 registration mode 使用闭合规则：

| registration mode | 字段状态                 | 结果                         |
| ----------------- | ------------------------ | ---------------------------- |
| public single     | missing / 精确 `False`   | 两参数 callback              |
| public single     | 精确 `True`              | 三参数 callback              |
| public single     | 其他值                   | 重建失败，脱敏错误           |
| mapped            | missing / 精确 `False`   | 既有 mapped 两参数 callback  |
| mapped            | 精确 `True` 或其他值     | 重建失败，脱敏错误           |

该字段：

- 只存在于可信 parent→worker registration 传输；
- 不来自 project JSON、REST request 或 capability response；
- 不改变 `serialized`/`lazyBuiltin`/`unavailable` 的含义；
- 不使 lazy `table_matmul@1` 存在；
- 不使 unavailable registration 变得可重建；
- 不绕过 callback/source/path/secret/raw exception 的白名单隔离。

Studio worker 自身仍调用 `plan.execute(..., options=None)`，因此被 Studio 执行的
opt-in provider 只会收到空 settings 和 `deadline=None`。把 Studio preview 限额映射
到执行 options 需要单独契约，不属于 5.2。

| Studio REST/OpenAPI/generated TS   | 否            | 必须无漂移                                      |
| project v2/checkpoint              | 否            | 必须无漂移                                      |
| capability schema v1               | 否            | 不加字段、不升版本                              |

结论：必须经过 `cf-api-designer`。需要其在实现前冻结 Python 构造器、时间精度、
错误映射、provider opt-in 名称/签名、Rust accessor 和 private binding 表面。

## 12. 验收矩阵

| #   | 层面                     | 验收                                                                                                       |
| --- | ------------------------ | ---------------------------------------------------------------------------------------------------------- |
| 1   | Python value object      | 顶层可导入；空构造得到空 settings、无 deadline；对象语义不可变                                             |
| 2   | settings copy            | 构造后修改 caller 根/嵌套容器不影响对象；修改读取副本也不影响对象                                          |
| 3   | strict JSON              | 非 mapping、非字符串 key、surrogate 字符串、非 JSON 类型、NaN/Inf、越界 int、循环、深度超限均被拒绝且脱敏 |
| 4   | deadline                 | aware offset datetime 归一化为 UTC，同一 instant 与微秒精度保持                                            |
| 5   | deadline errors          | naive/non-datetime/无效 offset/UTC 归一化越界给出稳定、脱敏 Python 错误                                    |
| 6   | omitted options          | sync/async 不传 options 的结果、异常、state 与基线相同                                                     |
| 7   | native plumbing          | sync/async 均把同一 settings/deadline 放入实际 Rust `RunContext`                                           |
| 8   | opted-in sync provider   | 第三个参数含规范化 settings/UTC deadline，不能反向修改 caller 或后续 operator                              |
| 9   | opted-in async execution | 通过 `execute_async` 运行时看到与同步相同的第三参数契约                                                    |
| 10  | legacy provider          | 未 opt-in 的既有 callback 仍只接收两个参数                                                                 |
| 11  | concurrent isolation     | 同一 plan 两个 async 调用的 settings/deadline 不串扰；lock 等待不延长绝对 deadline                         |
| 12  | expired deadline         | 已过期时 operator 调用计数为 0，返回现有取消错误                                                           |
| 13  | cooperative deadline     | 节点间到期在下个安全检查点取消；post-check 的 cancellation/deadline 保持优先于 callback error             |
| 14  | rollback                 | deadline/cancel/provider error 后 state 恢复，前置 recovery/input/snapshot 错误优先级不变，后续执行成功   |
| 15  | asyncio cancellation     | 锁等待取消不建 marker；执行中取消只恢复一次；无重复 completion、token/task 泄漏，plan 仍可复用            |
| 16  | registration             | flag 只接受精确 bool；失败/重复注册不推进 capability revision                                              |
| 17  | worker reconstruction    | serialized public registration 的 False/True round-trip 正确；未知 flag 脱敏失败；mapped/built-in 行为不变 |
| 18  | 5.1 stability            | capability v1 snapshot/JSON、catalog/capabilities、worker transportability 判定全部保持                    |
| 19  | schema stability         | project v2、checkpoint、OpenAPI、generated TypeScript 对基线无差异                                         |
| 20  | type surface             | Python export、wrapper signature、`_native.pyi`、类型检查与文档一致                                        |
| 21  | docs                     | 明确 absolute/cooperative deadline、strict JSON、opt-in callback、与 Studio limits 分离                    |
| 22  | full gates               | Rust/PyO3/Python/Studio/ruff/format/doc/stub 与生成工件检查全绿                                             |

测试 provider 应记录收到的 settings/deadline、调用次数和 state 变更；不得只测试
`ExecutionOptions` 值对象而没有通过真实 plan/operator 路径。

## 15. 风险与缓解

### 15.1 隐性 Python source break

风险：无条件三参数 callback 或签名探测会破坏现有 provider。

缓解：默认 `False` 的显式 opt-in；legacy callback 回归测试。

### 15.2 “不可变”只做浅冻结

风险：嵌套 dict/list 可改变运行语义。

缓解：规范化内部快照；属性返回副本；跨 operator 防串改测试。

### 15.3 时间精度或时区漂移

风险：浮点 epoch 丢微秒，naive datetime 被机器本地时区解释。

缓解：只收 aware datetime；UTC 归一化；非浮点 private transport；offset/微秒测试。

### 15.4 deadline 被误解为抢占

风险：同步 Python callback 阻塞时无法及时终止。

缓解：文档和测试明确 cooperative 安全检查点，不承诺线程中断。

### 15.5 options 被误接入 Studio

风险：把 preview limits 或 REST project payload 混入 settings，扩大远程执行面。

缓解：Studio 继续默认 options；REST/OpenAPI/project schema 无差异测试。

### 15.6 5.1 schema 被顺手扩展

风险：把 callback opt-in 放进 capability v1，破坏闭合 decoder 和外部客户端。

缓解：flag 只存在于注册 API 与可信 worker 私有投影；capability v1 golden 测试。

### 15.7 secret 泄露

风险：settings 常用于连接信息，异常/repr/log 可能泄露。

缓解：错误只含路径/类别；`repr` 不含内容；worker/raw exception 继续白名单脱敏。

## 16. API designer 已冻结的最小决策

`.codex/artifacts/api-notes/dal-5-5-2.md` 已固定：

1. provider opt-in 名称为
   `accepts_execution_options: bool = False`，仅接受精确 bool；
2. `ExecutionOptions` 是 `calc_flow.execution` 中的纯 Python、冻结、slots 值对象，
   顶层导出，并由 package-private factory 从真实 `RunContext` 重建；
3. strict JSON 使用 label-aware 私有纯函数、深度 32、serde portable integer
   范围和不回显 object key/value 的脱敏结构路径；API note 固定完整错误类别与文案；
4. private deadline transport 为
   `YYYY-MM-DDTHH:MM:SS.ffffffZ`，严格 UTC、六位微秒，不使用浮点 epoch；
5. Rust 新增公开借用 accessor
   `RunContext::deadline() -> Option<&DateTime<Utc>>`；`OperatorContext`
   不重复新增 accessor；
6. `execute_async()` 保持当前“普通方法返回 Awaitable”的兼容形态；
7. mapped provider 不 opt-in；worker 上的 mapped true flag 必须脱敏失败；
8. capability v1、Studio REST/OpenAPI/generated TypeScript、project v2 和 checkpoint
   均保持不变。

建议 critic 特别检查：

- provider opt-in 是否确实覆盖真实 operator 路径而非只覆盖值对象；
- deadline 在 plan lock 等待、首次 operator 前与 rollback 之间的顺序；
- Python async cancellation 和 deadline 同时发生时是否仅完成/回滚一次；
- worker registration flag 是否只来自可信 parent snapshot；
- capability v1、OpenAPI、project v2 和 generated TypeScript 是否严格无变更；
- 错误、repr、worker reconstruction 是否可能泄露 settings 或 raw exception。
